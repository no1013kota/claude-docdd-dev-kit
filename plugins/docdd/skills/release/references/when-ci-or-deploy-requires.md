# release：CI や反映コマンドがそう求める場合だけ使う手順

このプロジェクトの CI や反映コマンドが下の形になっていなければ、このファイルは使わない。手順の番号は `SKILL.md` の「『確認してから公開』『コマンドで公開』の経路」のもの。

## CI の軽量化の印

利用者の CI に「HEAD のメッセージに印（例: light ci）があれば本体（ビルド・E2E など）を飛ばす」仕組みがあるときだけ、手順1（CI の要否）で「不要」になった変更に印を付ける（コミットを書き換えない）。

```bash
git commit --allow-empty -m "chore(release): CI 軽量化（<理由: docs のみ 等>） [light ci]"
```

軽量化しても workflow 自体は動くので、手順3（CI を待つ）では型検査・lint など残りの部分の完了まで待つ。GitHub Actions 以外の CI なら、その CI の省略の仕組みがあればそれに従い、無ければ CI を回す。

## 反映コマンドの出力の読み方

- migration があり、コマンドが「適用したのでもう1回実行する」よう求める作りなら、その指示どおりもう1回実行する（求めなければ1回で終える）。
- コマンドが結果の項目や「デプロイ後の検証」（人間確認・実物で1周 など）を出す作りなら、その各項目まで読む。
- コマンドが CI の結果を見る作りで「CI 結果が見つからない」と出たら、push 漏れか軽量化の印の誤りを疑う。
- コマンドがホスティング側のビルドの完了を待たずに「build 中」で止まる作りなら、少し（例: 1〜2分）待って再実行する。

## DB の接続先を切り替える反映

- 切り替えと戻しの手順は『本番へ反映』行に書かれているものだけを使う（書かれていなければ切り替えず、止めて運営者に確認する）。
- 切り替えたら、**終わったら必ず staging へ戻す**（戻し忘れると次の staging 反映が本番 DB を見る）。

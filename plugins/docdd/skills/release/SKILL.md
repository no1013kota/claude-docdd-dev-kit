> **前提（docdd）**
> - 最初に `tasks/BACKLOG.md` と、`CLAUDE.md` の「検証コマンド」表があるかを確かめる。どちらかが無ければファイルを作らず、「先に `/docdd:init` を実行してください」と伝えて止まる。
> - `/docdd:init`・`/docdd:release`・`/docdd:update-kit` は運営者が自分で打つコマンドで、Claude のスキル一覧には出ない。一覧に無いことを不具合として伝えない。止まるときは要望の中身の検討を始めない。
> - 表の場所: 「検証コマンド」「反映コマンド」「スキルへの追加指示」は `CLAUDE.md`、「変更影響 → 必須の検証」・Definition of Done・規約は `.claude/rules/docdd-kit.md`（v0.1 系で導入したプロジェクトでは全部 `CLAUDE.md` にある。`/docdd:update-kit` で移せる）。
> - `CLAUDE.md`「スキルへの追加指示」にこのスキルの行があれば、本文より優先する。
> - 表の値が「無い」の行は飛ばし、二重波かっこ（`{{…}}`）のままの行は未記入として実行しない。どちらも理由を報告する（黙って省略しない）。
> - 課金・AI・ジョブ・決済など、このプロジェクトに無い機能についての手順は飛ばして「該当なし」と報告する。要決定には積まない。

# release：本番へ反映する

運営者から受けた依頼を**全部終えてから**1回だけ実行する。途中のタスクはローカルにコミットを積み、ここでまとめて push する（CI は push ごとに走り、時間がかかるため）。

使う値は `CLAUDE.md`「反映コマンド」表の『作業ブランチ』『本番ブランチ』『反映の方式』『staging へ反映』『本番へ反映』『公開先 URL』行。**「無い」の行の手順は飛ばして報告に理由を書く**（手で代わりの操作をしない）。

CI や反映コマンドが、印・再実行・DB の接続先の切り替えを求める作りのときだけ、`references/when-ci-or-deploy-requires.md` を読む。

## 0. 前提を確かめる（どの方式でも。1つでも欠けたら止まる）

1. **反映の方式**: `CLAUDE.md`「反映コマンド」表の『反映の方式』行を読み、進む経路を決める。

   | 『反映の方式』行 | 進み方 |
   |---|---|
   | A: 本番ブランチへ push するとホスティングが自動で公開 | §0 → 「方式 A の短い経路」だけ。「方式 B・C の経路」（CI の要否・staging・PR）は使わない |
   | B: staging を確認してから本番ブランチへ PR | §0 → 「方式 B・C の経路」の手順1〜8 |
   | C: 反映コマンドを実行 | §0 → 「方式 B・C の経路」の手順1〜8 |
   | まだ公開しない | **反映しない。** 「『反映の方式』が『まだ公開しない』なので反映しません。公開するときはこの行を書き換えてから、もう一度 `/docdd:release` を実行してください」と伝えて止まる |
   | 未記入・行が無い・上のどれでもない | 推測しない。上の4つを示して運営者に聞き、止まる（行が無い v0.1 系の `CLAUDE.md` なら `/docdd:update-kit` も案内する） |

2. **ブランチ**: 『作業ブランチ』『本番ブランチ』行が埋まっている（未記入なら推測せず運営者に聞いて止まる）。`git status --porcelain` が空で、今いるブランチが作業ブランチ。
   - 方式 A で2つが違うときは止まって聞く。「作業ブランチをそのまま本番ブランチにする（2つの行を同じ名前にする）」か「方式 B にする（『staging へ反映』行を「無い」にすれば PR だけの経路になる）」かを選んでもらう。
   - 方式 B で2つが同じなら、PR が作れないので止まって聞く。
3. **検証**: 各タスクで変更影響表（`.claude/rules/docdd-kit.md`「変更影響 → 必須の検証」）の該当行を実行済み（未実行の行は報告に書く）。`CLAUDE.md`「検証コマンド」表の『型検査』『lint』『単体・DBテスト』行が、直近の変更の後に1回緑。
   - 『未記入欄の検査』行も実行する。見つかっても止めず、出た `ファイル:行` を本番へ出す前の承知の提示と「報告」に並べる（「反映コマンド」表の未記入は手順1・2で止まる）。
4. **テスト基盤の固定行**: 報告に必ず次の1行を出す。`テスト基盤: 単体=有/無・E2E=有/無（無なら T-xx）`（両方「有」なら括弧は省く）
   - 『単体・DBテスト』行、『E2E（実ブラウザ）』行が「無い」または未記入なら、それぞれ「無」。
   - T-xx は基盤導入タスク（`tasks/BACKLOG.md` で、タイトルが「テスト基盤の導入」で始まり、状態が `done`・`dropped` 以外のタスク）の ID。無ければ報告で、単体が「無」なら `/docdd:add-task テスト基盤の導入`、E2E が「無」なら `/docdd:add-task テスト基盤の導入（E2E）` を案内する。
   - **単体も E2E も「無」のとき**: `tasks/BACKLOG.md`「要決定・外部準備（ユーザー作業）」に、論点「テスト無しで本番反映する」で状態が「決定」（テスト無しで反映する案を採った）の D-x があるかを見る。
     - あれば、固定行の末尾に `承知済み(D-x)` と付けて進む。
     - 無ければ**止まって聞く**。「テストが1つも無いので、壊れても公開先で初めて気付きます。先にテスト基盤を入れますか、テスト無しで反映しますか」。テスト基盤を入れるなら、基盤導入タスクがあれば `/docdd:dev-loop T-xx`、無ければ `/docdd:add-task テスト基盤の導入` を案内して止まる。テスト無しを選んだら、次の形で要決定に追記し、`tasks/BACKLOG.md` だけを `git add` してコミットしてから §0 をやり直す。聞くのは1回だけで、次からはこの記録を見て進む。

       ```markdown
       **D-<番号>: テスト無しで本番反映する** — 単体テストも E2E も無いまま本番へ反映するか。
       - 状態: 決定（YYYY-MM-DD, 案B）→ 書き戻し先: なし
       - 案A（推奨）: 先にテスト基盤を入れる（基盤導入タスクを進めるか、`/docdd:add-task テスト基盤の導入`）。反映が遅れる
       - 案B: テスト無しで反映する。壊れても公開先で初めて気付く
       ```
5. **gh（GitHub の操作コマンド）**: 方式 B・C で、`git remote get-url origin` が GitHub を指し、手順3（CI を待つ）か手順5（PR）で `gh` を使うなら、**push の前に** `gh auth status` を実行する。`gh` が無い、または未ログインなら push せずに止まり、次のどちらにするかを運営者に聞く。
   - `gh auth login` でログインしてから、もう一度 `/docdd:release` を実行する。
   - PR は GitHub の画面で作る（手順3の CI の結果と手順5の PR 作成・マージは、運営者に画面で行ってもらい、終わったと言われてから進む）。
6. **sandbox**: 「反映コマンド」表のコマンドは **sandbox 外**で実行する（公開先へ接続するため。sandbox 内では名前解決に失敗することがある）。
7. **引数 `staging`**: 方式 B・C なら手順4で終える。方式 A には staging が無いので、push せずに「方式 A には staging がありません」と伝えて止まる。

## 共通の手順（方式 A と方式 B・C の両方から使う）

### 反映コマンドの結果を判定する

終了コード（0 以外なら失敗）とエラー出力で判定し、❌ や失敗があれば止まる。出力が「もう1回実行する」「少し待って再実行する」などを求める作りなら、`references/when-ci-or-deploy-requires.md` の「反映コマンドの出力の読み方」に従う。

### ホスティングのビルド成功を待つ

本番ブランチの最新コミットのデプロイ（ホスティング側のビルド）が成功になるまで待つ。

- ホスティングが GitHub のコミットへ status を返すなら、`gh api repos/<owner>/<repo>/commits/<sha>/status` を一定間隔で見る（例: 15秒間隔・最大8分）。
- status が返らない（空のまま）なら、『本番へ反映』行のコマンドがビルドの完了待ちを兼ねる作りならそれに任せる。そうでなければ、ホスティングの画面で本番ブランチの最新デプロイが成功したことを確かめてから進む（自分で確かめられなければ運営者に確認して止まる）。
- 失敗なら止めて、ホスティングのログの要点と「公開中の版が前のままか」を運営者に報告する（revert や force push を勝手にしない）。

### 実ブラウザで確認する

**一時スクリプトは書かない。** 変更した画面を『公開先 URL』行で開き、`/docdd:playwright-cli` の `open`・`console`・`requests`・`eval` で確かめる。スクショを撮るなら置き場は `/tmp/claude/`（リポジトリに置かない）。`playwright-cli` が使えなければ `/docdd:playwright-cli` の手順で用意する（入れてよいか運営者に聞く）。

- 見るもの: HTTP 200・コンソールエラー 0・失敗したリクエスト無し・画像やグラフが描画されている（画像は `eval` で `naturalWidth > 0` まで見る。遅延読み込みは `eval` でページの下までスクロールしてから判定する）。
- 公開先では**読むだけ**にする（ログイン・入力・送信などデータを書き換える操作をしない）。

### 報告

- テスト基盤の固定行（§0 手順4）
- 反映の方式・PR（番号か URL）・本番 URL・確認した画面と結果
- **CI の要否とその理由**・migration の有無
- 未記入欄: §0 手順3 の『未記入欄の検査』で出た `ファイル:行`（無ければ「なし」）
- 実物で1周した検査の費用（回したとき）
- 飛ばした手順と理由（「無い」の行・未記入の行を含む）

## 方式 A の短い経路（本番ブランチへ push すると自動で公開される）

「方式 B・C の経路」（CI の要否判断・staging・PR）は使わない。**push がそのまま本番への反映になる**ので、push の前に必ず承知を得る。

1. **前提**: §0 をすべて満たす。加えて `CLAUDE.md`「検証コマンド」表の『全検査（push 前に1回）』行を実行して緑にする（「無い」なら『ビルド』行と『E2E（実ブラウザ）』行。どれも「無い」・未記入なら理由を報告に書く）。
2. **運営者の「はい」を得る**: 次を示して聞く。
   - 変更一覧: `git log --oneline origin/<本番ブランチ>..HEAD` のコミット（まだ一度も push していなければ `git log --oneline`）
   - migration（DB のスキーマ変更）の有無: `git diff --name-only origin/<本番ブランチ>...HEAD` に含まれるか。含まれるなら本番 DB への適用方法（『本番へ反映』行）も示す。その行が「無い」・未記入なら push せず、適用方法を運営者に聞いて止まる
   - 本番 URL: 『公開先 URL』行
   - テスト基盤の固定行と、1 の検査の結果
   - 未記入欄: §0 手順3 の『未記入欄の検査』で出た `ファイル:行`

   **明示の「はい」以外なら push しない**（ローカルのコミットはそのまま残して止まる）。許可の確認ダイアログ（「このコマンドを実行してよいか」）で許可されたことは、この承知の代わりにならない。
3. **push（1回だけ）**: `git push origin <本番ブランチ>`
4. **ホスティングのビルド成功を確かめる**: 「共通の手順」の「ホスティングのビルド成功を待つ」。『本番へ反映』行にコマンドがあれば、ビルド成功の後にそれを実行し、「反映コマンドの結果を判定する」で判定する。
5. **実ブラウザで確認する**: 「共通の手順」の「実ブラウザで確認する」。
6. **報告**: 「共通の手順」の「報告」。PR と CI の要否は「方式 A のため無し」と書く。

## 方式 B・C の経路

### 1. CI の要否を決める（判断ではなく対応表で）

`git diff --name-only origin/<本番ブランチ>...HEAD`（例: `origin/main...HEAD`）の全ファイルを次の表に当てる。**1つでも「必要」に当たれば CI を回す。表のどちらにも当たらないファイルがあれば「必要」**。運営者が「CI なしで」と言っていても、「必要」に当たる変更なら理由を添えて CI を回す（逆に運営者が「CI ありで」と言えば従う）。

| 変更したファイル | CI |
|---|---|
| アプリ本体のコード（下の「不要」に当たらないソースコード）・DB の migration・E2E テスト・依存（`package.json`・lock ファイルなど）・設定ファイル（フレームワーク・型検査・テストランナー・E2E・ホスティングのもの）・CI の定義（GitHub Actions なら `.github/workflows/**`）・`scripts/**`・公開する静的ファイル・`.env.example` | **必要** |
| `docs/**`・`tasks/**`・`.claude/**`・ルートの `*.md`（`CLAUDE.md`・`README.md` 等）・`.gitignore`・`.mcp.json` | 不要（`CLAUDE.md`「検証コマンド」表の『docs の検査』行と『単体・DBテスト』行が緑であること） |

「不要」でも、push すれば CI は丸ごと走る。CI の定義に「印があれば本体を飛ばす」仕組みがあるときだけ、`references/when-ci-or-deploy-requires.md` の「CI の軽量化の印」を使う。仕組みが無ければ印を付けずに CI を回す（「必要」と同じ扱い。仕組みを足すかは運営者の判断＝要決定へ）。

### 2. push（1回だけ）

```bash
git push origin <作業ブランチ>     # 例: git push origin stg
```

### 3. CI を待つ

CI があるなら、push した HEAD の CI が完了するまで待つ。CI が無いプロジェクトだけ、この手順を飛ばして報告に書く。

GitHub Actions なら、Monitor で `gh run list --branch <作業ブランチ> --json headSha,status,conclusion` を HEAD の SHA で突き合わせ、`completed success` まで待つ。他の CI なら、その CI の画面かコマンドで HEAD の SHA の結果を確かめる。赤なら **ここで止めて原因を直す**（GitHub Actions なら `gh run view <id> --log-failed`）。直したら §0 からやり直す。

### 4. staging

『staging へ反映』行を実行する（「無い」なら飛ばす）。「共通の手順」の「反映コマンドの結果を判定する」で判定する。

### 本番へ出す前の承知（手順5・6 の直前。省略しない）

次を示し、**運営者の明示の「はい」を得てから**手順5・6へ進む（手順5と6をまとめて1回聞けばよい）。

- 変更一覧: `git log --oneline origin/<本番ブランチ>..HEAD` のコミット（タスクID が分かる形で）
- migration（DB のスキーマ変更）の有無
- 本番 URL: 『公開先 URL』行
- CI の要否と結果・staging の確認結果・テスト基盤の固定行
- 未記入欄: §0 手順3 の『未記入欄の検査』で出た `ファイル:行`

「はい」以外なら進まない（staging まで反映した状態で止め、そのことを報告する）。**許可の確認ダイアログ（「このコマンドを実行してよいか」）で許可されたことは、この承知の代わりにならない。**

### 5. 本番ブランチへ取り込む（PR）

方式 C で作業ブランチと本番ブランチが同じなら、この手順は飛ばして手順6へ。

GitHub で `gh` が使えるなら:

```bash
gh pr create --base <本番ブランチ> --head <作業ブランチ> --title "release: <内容>（<タスクID>）" --body "<内容・検証・migration の有無>"
gh pr merge <URL> --merge --delete-branch=false
git checkout <本番ブランチ> && git pull -q origin <本番ブランチ>
```

§0 で「PR は GitHub の画面で作る」を選んだなら、`https://github.com/<owner>/<repo>/compare/<本番ブランチ>...<作業ブランチ>` を示し、PR の作成とマージを運営者に頼む。終わったと言われてから `git checkout <本番ブランチ> && git pull -q origin <本番ブランチ>` を実行する。GitHub でなければ、使っているサービスの PR（マージリクエスト）で同じ順に行う。

取り込んだら、「共通の手順」の「ホスティングのビルド成功を待つ」。

### 6. 本番

『本番へ反映』行を実行する（「無い」なら飛ばす。本番ブランチへの取り込みだけで公開される場合）。「共通の手順」の「反映コマンドの結果を判定する」で判定する。DB の接続先を切り替える作りなら、`references/when-ci-or-deploy-requires.md` の「DB の接続先を切り替える反映」に従う。

終わったら `git checkout <作業ブランチ>` で作業ブランチへ戻る。

### 7. 実ブラウザで確認する

「共通の手順」の「実ブラウザで確認する」。

### 8. 報告

「共通の手順」の「報告」。

## ルール

- 本番へ出す操作（方式 A の push、方式 B・C の手順5・6）は、運営者の「はい」を得てからだけ行う。
- 本番 DB へは『本番へ反映』行のコマンド以外で書かない（読むのは可）。
- force push・`git add -A`・コミットの書き換え（amend/rebase）をしない。軽量化の印は空コミットで足す。
- 途中で ❌ が出たら次の手順へ進まない。原因を直してから §0 へ戻る。
- **GitHub 公式の CI 省略の印（角括弧付きの skip ci など）はコミットメッセージに書かない**（本文で言及するときも角括弧を外す）。GitHub Actions はメッセージ全体を見て workflow ごと止め、必須チェックが報告されず PR がマージできない。軽量化は CI の側で「印があれば本体を飛ばす」形にし、その印（例: light ci）も空コミットの件名にだけ付ける。

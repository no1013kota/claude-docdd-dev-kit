> **前提（docdd）**
> - 最初に `tasks/BACKLOG.md` と、`CLAUDE.md` の「検証コマンド」表があるかを確かめる。どちらかが無ければファイルを作らず、「先に `/docdd:init` を実行してください」と伝えて止まる。
> - `/docdd:init`・`/docdd:release`・`/docdd:update-kit` は運営者が自分で打つコマンドで、Claude のスキル一覧には出ない。一覧に無いことを不具合として伝えない。止まるときは要望の中身の検討を始めない。
> - 表の場所: 「検証コマンド」「反映コマンド」「スキルへの追加指示」は `CLAUDE.md`、「変更影響 → 必須の検証」・Definition of Done・規約は `.claude/rules/docdd-kit.md`（v0.1 系で導入したプロジェクトでは全部 `CLAUDE.md` にある。`/docdd:update-kit` で移せる）。
> - `CLAUDE.md`「スキルへの追加指示」にこのスキルの行があれば、本文より優先する。
> - 表の値が「無い」の行は飛ばし、二重波かっこ（`{{…}}`）のままの行は未記入として実行しない。どちらも理由を報告する（黙って省略しない）。
> - 課金・AI・ジョブ・決済など、このプロジェクトに無い機能についての手順は飛ばして「該当なし」と報告する。要決定には積まない。

# dev-loop：開発サイクル1回転

バックログ駆動で**1タスクだけ**を完了させる（WIP = 1。同時に進めるタスクは常に1件）。


## ルール

- 外部要因（アカウント未作成・キー未発行など）で完了できないなら `blocked` にし、理由をBACKLOGへ書いて次へ進む。
- 運営者が不要と判断したタスクは消さずに `dropped` にし、理由を書く。
- 単体テスト基盤があるのに、振る舞いを変えた変更を単体テスト無しで完了扱いにしない。基盤が無い間は、基盤導入タスク（§1-2）の ID を添えて、単体テスト未実施を未検証事項として報告する。
- 必要な統合テスト・E2Eが未実施なら、単体テストだけで完了扱いにしない。環境不足なら未検証事項として明示する。
- テストが通らない状態でコミットしない。
- コミット前に `git status` を見て、無関係な変更を巻き込まない。
- Definition of Done は `.claude/rules/docdd-kit.md`。
- 続けて回すときは `/loop /docdd:dev-loop`。§1・§1-2・§2 の停止に当たったら、その回は何も変えずに止まった理由だけを報告する。

会話の圧縮のあとで、この手順書が途中までしか見えなければ、このスキルのフォルダの `SKILL.md` を Read で読み直してから続ける。

## 手順

### 0. 現状を正本から確認する（必須）

まず `node scripts/backlog-archive.mjs` を実行し、終わったタスクと決まった要決定を `tasks/archive/BACKLOG-done.md` へ移す（移すものが無ければ何も変えない。移したら `git add tasks/BACKLOG.md tasks/archive/BACKLOG-done.md` だけを行い、`chore(backlog): 終わったものをアーカイブへ移す` でコミットする。`scripts/backlog-archive.mjs` が無ければ `/docdd:update-kit` を案内し、移さずに進む）。

そのうえで `git log --oneline -15` と `tasks/BACKLOG.md` を読む。**記憶より git log と BACKLOG を信頼する**（会話が長くなると、記憶上の進捗が実際とずれる）。BACKLOG にあるのは、まだ動いているもの（`todo`・`doing`・`blocked` と未決の要決定）だけ。**アーカイブは丸ごと読まない**（育ち続けるので、読むだけで作業の場所を使う）。依存先や過去の経緯が要るときだけ、ID や言葉で検索する（例 `grep -n "T-12" tasks/archive/BACKLOG-done.md`）。

- 会話で要決定への回答（「D-1 は A」「推奨で」など）を受けていたら、タスクを選ぶ前に、**まず決まった内容を正本へ書き戻す**（事業判断は `docs/PRD.md` の該当節、画面・データの細部は `docs/requirements/` の担当文書、技術判断は ADR。分け方は `docs/decisions/README.md`）。PRD・requirements を直したら、冒頭の「更新日」を今日にし、変更履歴に 1 行（きっかけに D-番号）を足す（`docs/README.md` §4）。そのあとで該当 D-番号の「状態」行を `決定（YYYY-MM-DD, 案A）→ 書き戻し先: <反映した所>` に書き換え、`git add tasks/BACKLOG.md <反映したファイル>` とパスを明示して `chore(backlog): D-<番号> 決定` を 1 コミットにする。書き戻し先が「なし」の決定（release が記録するものなど）は反映しない。
  - 反映が 1〜2 行で済まないとき（ADR を 1 本書く、まだ無い節を起こすなど）は、「D-<番号> を正本へ書き戻す」S タスクを起票し、状態行は**未決のまま**残す（書き戻す前にアーカイブへ移らないようにする）。

### 1. タスクを選ぶ

| 状況 | すること |
|---|---|
| `doing` がある | それを再開 |
| 引数でID指定 | それを選ぶ |
| どちらも無い | 依存がすべて済んでいる（タスクは `done`、要決定は決定済み。依存先が BACKLOG に無ければアーカイブを ID で検索して確かめる）最優先の `todo` を1件（上にあるものほど優先） |
| `todo` が1件も無い | **実装を始めず停止。** `/docdd:add-task <やりたいこと>` で1件ずつ起票できること、仕様書からまとめて起票するなら `/docdd:tasks-from-docs` を伝える |

- `blocked`（外部要因で止まっている）と `dropped`（取り下げ）は選ばない。
- 未決の要決定（D-番号）に依存するタスクは飛ばす。**全部ブロックなら停止**して、必要な決定を D-番号ごとに列挙する。
- 依存する D-番号が決定済みなのに、書き戻し先（PRD の該当節や ADR）へまだ反映されていなければ、着手前に反映する。反映はこのタスクのコミットに含める（アーカイブへ移った D-番号も、「状態」行の書き戻し先で同じように確かめる）。
- 次の §1-2 を通ってから `doing` に更新する。

### 1-2. テスト基盤の門

`CLAUDE.md`「検証コマンド」表の『単体・DBテスト』行が「無い」または未記入（`{{…}}` のまま）なら、単体テスト基盤なしとして次の表で決める。行にコマンドが書いてあれば、この門はそのまま通る。

**基盤導入タスク**＝タイトルが「テスト基盤の導入」で始まり（「テスト基盤の導入（E2E）」も含む）、状態が `done`・`dropped` 以外のタスク。表は上の行から見て、最初に当てはまる行に従う。`done`・`dropped` のタスクはアーカイブへ移っているので、下の表の「`dropped` だけ」「`done` がある」「どこにも無い」は `tasks/BACKLOG.md` とアーカイブの両方で見る（`grep -n "テスト基盤の導入" tasks/archive/BACKLOG-done.md`）。

| `tasks/BACKLOG.md`（とアーカイブ）の状態 | すること |
|---|---|
| 選んだタスクが基盤導入タスク | そのまま進める |
| 基盤導入タスクがある | その ID を優先候補として示す。引数も `doing` も無く、そのタスクの依存が済んでいれば、そのタスクを選ぶ。引数で別のタスクを指定されていれば、そのまま進める |
| 「テスト基盤の導入」で始まるタスクが `dropped`（テストを持たないと決めた）だけ | そのまま進める |
| 「テスト基盤の導入」で始まるタスクに `done` がある（行は埋まっていない） | そのまま進め、`CLAUDE.md` の『単体・DBテスト』行を埋めるよう報告で伝える |
| 「テスト基盤の導入」で始まるタスクがどこにも無い | **着手せず停止**（`doing` にしない）。`/docdd:add-task テスト基盤の導入` を実行するよう案内する |

### 2. 仕様を読む（仕様の門）

タスクの「参照:」が指す節（`docs/PRD.md` の A-番号、`docs/requirements/` の見出し ID、そのほかの仕様書の見出し）を読む。どの文書が何を定義するかは `docs/README.md`。参照が `docs/operations/development-and-testing.md` の基盤タスクは、その節を読めばよい（この門の対象外）。 `参照: なし（振る舞いを変えない）` のリファクタ単位も対象外で、仕様は書かない（`/docdd:refactor` で進めるのが本筋。dev-loop で進めるならコミットは `refactor(<scope>): …`）。

**参照先の節が無い、または該当節に `{{…}}` が残っているなら §3 へ進まない。** 先に仕様を書く。

1. `docs/requirements/README.md` の分け方に従い、担当の文書に節を起こす。文書が無ければ新しく作る（冒頭に版・更新日の表、末尾に変更履歴を付ける）。節の見出しは同じ README の見出し ID の決まり（`## S-01 予約一覧` など）に従う。
2. タスクの完了条件から、仕様を 5〜10 行で下書きする。費用・契約を伴わない細かな選択は推奨案で書き、下書きの中で「推奨で書いた」と示す。
3. 費用・外部サービスの契約・利用者に見える選択で、運営者の判断が要るものは下書きで決めない。`tasks/BACKLOG.md` の「要決定」へ D-番号で積み、タスクの依存にその D-番号を足して `todo` に戻し、§1 からやり直す。
4. 下書きを運営者に **1 回だけ** 見せて確認する。承認されたら §3 へ進む。書いた仕様はこのタスクのコミットに含める。

### 3. 実装と単体テスト

- 完了条件を満たす**最小の実装**。タスクに無いスコープへ広げない。
- 正常系だけでなく、変更に関係する**異常系と境界値**を含める。
- 不具合修正は**修正前に失敗する再現テストを先に**追加する。
- 実装詳細ではなく公開される入出力・状態遷移・エラーを検証する。カバレッジ率（テストが通った行の割合）をテスト品質の代わりにしない。
- テスト追加が不要な変更（docs・コメント・機械的な設定）なら、その理由を §6 で報告する。
- 単体テスト基盤が無い間（§1-2）は、テストを書く代わりに「単体テスト未実施（テスト基盤なし・T-xx）」を未検証事項として §6 で報告する。テストの道具（ランナー）をこのタスクのついでに入れない。
- 実装中に出た細かい仕様の疑問は暫定判断で進めてよいが、**必ず §5 で docs へ残す**。疑問の節が `{{…}}` のままなら §2 に戻る。
- **技術選定（フレームワーク・DB・テスト基盤・主要なライブラリ）は暫定判断で決めない。** 選定が要ると分かったら実装を止める。「ADR 案を書く」S タスク（`docs/decisions/` に案と推奨を書き、運営者が承知したら完了）を `/docdd:add-task` と同じ書式で起票し、今のタスクの依存にその ID を足して `todo` に戻す。依存するパッケージは承知の後に入れる。
- 基盤導入タスク（§1-2）では、使う道具が要決定や ADR でまだ決まっていなければ、`docs/operations/development-and-testing.md` §4（テスト基盤が無いとき）の推奨を案として運営者に 1 回確認してから入れる（別タスクには分けない）。

### 4. 検証

**手段は変更影響表（`.claude/rules/docdd-kit.md`「変更影響 → 必須の検証」）で決める**（その場の判断で選ばない。新規実装か既存更新かでも分けない）。

- 触った層の該当行を**すべて**実行する。実行しなかった行は理由を報告する。
- いつ何を回すかと落とし穴は、`docs/operations/development-and-testing.md` §2（いつ回すか）・§5（落とし穴）を読んでから決める。

**このループ固有の注意**:

- 実装中は変更対象に近いテストを絞って反復し、失敗したら直してから進む。
- 完了前に `CLAUDE.md`「検証コマンド」表の『型検査』『lint』『単体・DBテスト』の3行を回す。「無い」行と未記入の行は実行せず、理由を報告する。
- 変更影響表の「画面（Web）」行か「画面・操作（Web 以外）」行に当たるのに、`CLAUDE.md`「検証コマンド」表の『E2E（実際に動かす）』行が「無い」または未記入なら、E2E の未実施理由に基盤導入タスク（§1-2）の ID を書く。基盤導入タスクが無ければ、`/docdd:add-task テスト基盤の導入（E2E）` を報告で案内する。
- **pass件数だけ見ない。** テストの fail・skip・todo を確認する。実 DB を使うテストの skip を統合テスト成功として扱わない。実行件数も見て、0 件なら緑にしない（例: Unity はテストが 0 件でも終了コード 0 で終わる。`-testResults` の XML の `total` を見る）。
- 該当スキル（`/docdd:verify-integration`・`/docdd:verify-e2e`）が使えないなら同等の検証を行い、代替内容と未検証事項を報告する。

### 5. docs同期

`/docdd:doc-sync` を実行する。**これを省略した完了は完了ではない。**

### 6. 完了処理と報告

- BACKLOG を `done` にし、「実装メモ:」（どう作ったか・後続が知るべき判断。1〜2 行）と「検証:」（変更影響表のどの行を回して何を見たか。回さなかった行と理由も）の 2 行を足してから、`node scripts/backlog-archive.mjs` でアーカイブへ移す（このタスクのコミットに `tasks/BACKLOG.md` と `tasks/archive/BACKLOG-done.md` を含める。スクリプトが無ければ移さずに進み、報告で `/docdd:update-kit` を案内する）。
- 基盤導入タスク自身は、完了条件の見本テスト（単体 1 件。画面があるなら E2E（実際に動かす）も 1 件）が緑（実行件数が 0 件でない。§4）になり、`CLAUDE.md`「検証コマンド」表の該当行が埋まったら完了とする。
- 新たなユーザー判断事項は「要決定」へ追記する（書式は `tasks/BACKLOG.md` の運用ルールの見本。可能なら推奨案を添える）。
- コミット前に `git status` を見て、このタスクと無関係な変更を巻き込まない。パスを明示して `git add` する。
- タスクの「参照:」が指す文書に、着手前からの未コミットの変更（運営者が自分で書き換えたもの）があれば、このタスクのコミットに含める。冒頭の「更新日」を今日にし、仕様が変わったなら変更履歴に 1 行（きっかけにタスク ID）を足す（`docs/README.md` §4）。
- タスクIDを含むメッセージでコミットする（例 `feat(T-01): メール認証を実装`）。
- 報告（この順）:
  - 完了したタスク
  - 主要な判断
  - 新しく書いた／埋めた仕様の節（§2 で書いたもの。無ければ「なし」）
  - 検証の結果と未検証事項（実行しなかった行と理由。運営者に確かめてもらう見た目・操作は「運営者確認待ち」として、開く場面・操作・期待する見え方を添える）
  - `テスト基盤: 単体=有/無・E2E=有/無（無なら T-xx）`（両方「有」なら括弧は省く。T-xx は基盤導入タスク（§1-2）の ID。無ければ T-xx の代わりに、単体なら `/docdd:add-task テスト基盤の導入`、E2E なら `/docdd:add-task テスト基盤の導入（E2E）` と書く）
  - 次のタスク
  - 新たな要決定（D-番号ごとに「A」「B」で答えればよい。全部推奨でよければ「推奨で」）

> **前提（docdd）**
> - 最初に `tasks/BACKLOG.md` と、`CLAUDE.md` の「検証コマンド」表があるかを確かめる。どちらかが無ければファイルを作らず、「先に `/docdd:init` を実行してください」と伝えて止まる。
> - `/docdd:init`・`/docdd:release`・`/docdd:update-kit` は運営者が自分で打つコマンドで、Claude のスキル一覧には出ない。一覧に無いことを不具合として伝えない。止まるときは要望の中身の検討を始めない。
> - 表の場所: 「検証コマンド」「反映コマンド」「スキルへの追加指示」は `CLAUDE.md`、「変更影響 → 必須の検証」・Definition of Done・規約は `.claude/rules/docdd-kit.md`（v0.1 系で導入したプロジェクトでは全部 `CLAUDE.md` にある。`/docdd:update-kit` で移せる）。
> - `CLAUDE.md`「スキルへの追加指示」にこのスキルの行があれば、本文より優先する。
> - 表の値が「無い」の行は飛ばし、二重波かっこ（`{{…}}`）のままの行は未記入として実行しない。どちらも理由を報告する（黙って省略しない）。
> - 課金・AI・ジョブ・決済など、このプロジェクトに無い機能についての手順は飛ばして「該当なし」と報告する。要決定には積まない。

# doc-sync：ドキュメント同期

`/docdd:dev-loop`・`/docdd:refactor`・`/docdd:speed-up`・`/docdd:security-audit`・`/docdd:ui-polish` は中でこのスキルを呼ぶ。**スキルを通さずに自分でコードを直したときは、コミットの前に自分で打つ**（仕様書と実装がずれたままコミットしない）。

コードとドキュメントの乖離（ずれ）を検出し、**その場で解消する**。

## 手順

1. **範囲を決める** — 引数が `--full` なら下の「--full（監査モード）」へ。ほかの引数があれば `git diff <引数>`、なければ未コミットの変更（`git diff HEAD` ＋ 未追跡ファイル）。
2. **影響先を判定する** — `docs/README.md` §1 の地図と §2 の所有ルール（雛形の場合。自前の `docs/README.md` なら「どこに何があるか」「どこに書くか」相当の節）で決める。
3. **突き合わせて更新する** — 下の「書き方」。
4. **検査を回す** — `CLAUDE.md`「検証コマンド」表の『docs の検査』行と『未記入欄の検査』行を実行する。
   - どちらも git が追跡しているファイルだけを見る。新しく作った文書は、先に `git add <そのパス>` しないと「実在しない」と報告される。
   - 『docs の検査』が落ちたら、直してから次へ進む。ただし、落ちた行がキットの置いていない既存の文書（導入前からある自前の文書など）にあり、今回の変更（手順 1 の範囲）が原因でない（参照先を動かしても消してもいない）なら、勝手に直さない。報告に `ファイル:行 → 参照先` を載せ、運営者の承知を得て直すか、そのまま次へ進む。直し方の案として、その行に「例」の字を入れるか、コードブロックか HTML コメントに入れるかを添える（どちらも検査の対象から外れる）。
   - 『未記入欄の検査』で `{{…}}` が見つかっても、コミットは止めない。見つかった `ファイル:行` を報告に列挙する。
   - BACKLOG のアーカイブ漏れを見る: `node scripts/backlog-archive.mjs --check` を回す。残っていると言われたら `node scripts/backlog-archive.mjs` で移し、`tasks/BACKLOG.md` と `tasks/archive/BACKLOG-done.md` を**このあとのコミットに含める**（このスキルではコミットしない。移した件数を報告に書く）。`scripts/backlog-archive.mjs` が無ければ飛ばし、報告で `/docdd:update-kit` を案内する。
   - 検査が見ない所は目で確かめる: `tasks/BACKLOG.md` の `todo`・`doing` のタスクの「参照:」が指す文書と節（PRD の A-番号か節・requirements の見出し ID（ID を付けない文書は見出し）・そのほかの仕様書の見出し）が実在するか。無ければ報告に書く（参照に「（削除）」の付いた節は、無いのが正しいので除く）。
5. **報告する** — 表形式。「影響なし」も理由付きで書く。黙って省略しない。

   | 変更内容 | 影響ドキュメント | 対応 |
   |---|---|---|
   | 一覧取得APIを追加 | `docs/requirements/` の担当文書 | 更新済み |
   | リファクタのみ | — | 影響なし（外部仕様の変更なし） |

   表の下に「未記入欄（`ファイル:行`）」と「参照の切れ（タスク ID と、見つからない参照先）」と「直さなかった『docs の検査』の失敗（`ファイル:行 → 参照先`）」を並べる。無ければ「なし」と書く。

## 書き方

- **仕様レベルで書く。** コードの逐語的な説明にしない。
- 数値・一覧は**同じものを2か所に置かない**（片方だけ古くなる）。所有先は `docs/README.md` §2（雛形の場合。自前なら「どこに書くか」相当の節）。
- 更新した文書は冒頭の**更新日**を直す。仕様が変わったなら末尾の**変更履歴**にも追記し、「内容」の末尾に**きっかけ**（`T-01`・`D-1`・「運営者の指示 YYYY-MM-DD」）を添える。分からなければ省く。
- 要件そのものが変わるときだけPRDを更新する。
- **新しい一覧や数値を書くなら、突き合わせる検査も同時に作る**（既存の仕組みは `docs/README.md` §3。雛形の場合。自前なら「ずれを止める仕組み」相当の節）。作れないなら「実測が正」と明記して日付を添える。
- docsに無い設計判断が実装に入っていたら `docs/decisions/` へ ADR を追加し、**同じコミットで `docs/decisions/README.md` の「ADR 一覧」にも 1 行足す**（足し忘れは『docs の検査』が落とす）。

## --full（監査モード）

差分ではなく実装全体と `docs/` を突き合わせ、3種の乖離を列挙して直す。

| 種別 | 内容 |
|---|---|
| (a) | docsに記載があるが未実装（未実装が正しいなら「未実装」と明記されているか） |
| (b) | 実装されているがdocsに記載がない |
| (c) | 記述が実装と食い違って古い |

対象が広いので、機能領域ごとにサブエージェントへ並列で分担させてよい。直し終えたら手順 4・5 を行う。

### docs が雛形のままのとき

コードが先にあるプロジェクトへ docdd を入れた直後は、`docs/PRD.md` の機能一覧が `{{…}}` のままで、`docs/requirements/` に説明と見本しか無いことが多い。このとき (b) が大量に出るので、次の順で docs を起こす。

1. (b) の一覧を機能領域（画面・データ・処理・API など）ごとにまとめ、`docs/requirements/README.md` の分け方に従って `docs/requirements/0N_<名前>.md` に起こす。各文書は冒頭に版・更新日の表、末尾に変更履歴を持つ（`docs/requirements/00_template.md` があれば写す）。節の見出しは見出し ID の決まり（`## S-01 予約一覧` など）に従う。
2. 件数・上限・時間などの数値は、突き合わせる検査が無ければ「実測が正（YYYY-MM-DD 時点）」と日付を添える。
3. 実装済みの機能を `docs/PRD.md` §3.1（雛形の場合。自前の PRD なら「機能一覧」相当の節）に A-番号（`A-1` など）で足す。
4. スコープ・料金・公開範囲などの事業判断は、コードから推測して書かない。`tasks/BACKLOG.md` の「要決定・外部準備（ユーザー作業）」へ D-番号で積む。
5. 最後に `CLAUDE.md`「検証コマンド」表の『docs の検査』行を回す（新しい文書は先に `git add`。落ちたら手順 4 のとおり直すか、報告に載せる）。そのうえで、起こした文書・PRD・BACKLOG をパスを明示して stage し、1 コミットにまとめる（例 `docs: 既存の実装から仕様を起こす`）。
6. 報告の最後に次の一手を書く。docs に書いてあって、まだ作っていない所（(a)）があれば何も書かずに `/docdd:add-task`、無ければ `/docdd:add-task <やりたいこと>`。

## 注意

- **このスキル内で完結させる。**「あとで更新する」で終わらせない。
- **これから作る仕様は戻さない。** `docs/` の未コミットの書き換え（運営者が先に書いたもの）と、`tasks/BACKLOG.md` の `todo`・`doing` のタスクが参照する節は、実装と違っても、実装に合わせて元へ戻さない。実装で決めた細部を書き足してよいのは、`/docdd:dev-loop` から呼ばれたとき（そのタスクが参照する節）だけ。`/docdd:refactor`・`/docdd:speed-up`・`/docdd:security-audit` から呼ばれたときは、運営者の未コミットの書き換えがある文書を直さず、直す中身を報告に書く。どのタスクも参照していない書き換えは、報告に並べる（運営者が「コミットして」と頼んだ docs だけの変更なら、そのままコミットへ進んでよい。仕様をタスクにしたいなら、何も書かずに `/docdd:add-task`）。
- PRD のスコープ（`docs/PRD.md` §3.2「やらないこと」。雛形の場合。自前の PRD なら「やらないこと」相当の節）に反する実装を検出したら、更新せずユーザーに警告する。

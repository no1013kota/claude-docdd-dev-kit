> **前提（docdd）**
> - 最初に `tasks/BACKLOG.md` と、`CLAUDE.md` の「検証コマンド」表があるかを確かめる。どちらかが無ければファイルを作らず、「先に `/docdd:init` を実行してください」と伝えて止まる。
> - `/docdd:init`・`/docdd:release`・`/docdd:update-kit` は運営者が自分で打つコマンドで、Claude のスキル一覧には出ない。一覧に無いことを不具合として伝えない。止まるときは要望の中身の検討を始めない。
> - 表の場所: 「検証コマンド」「反映コマンド」「スキルへの追加指示」は `CLAUDE.md`、「変更影響 → 必須の検証」・Definition of Done・規約は `.claude/rules/docdd-kit.md`（v0.1 系で導入したプロジェクトでは全部 `CLAUDE.md` にある。`/docdd:update-kit` で移せる）。
> - `CLAUDE.md`「スキルへの追加指示」にこのスキルの行があれば、本文より優先する。
> - 表の値が「無い」の行は飛ばし、二重波かっこ（`{{…}}`）のままの行は未記入として実行しない。どちらも理由を報告する（黙って省略しない）。
> - 課金・AI・ジョブ・決済など、このプロジェクトに無い機能についての手順は飛ばして「該当なし」と報告する。要決定には積まない。

# maintenance：定期点検

**コードを変えていなくても、時間がたつと変わるもの**を点検する。CIとテストは「変更したときに」走るが、外部APIの仕様変更・新しい脆弱性・データの滞留・控えの古さ・費用の増加は**時間の経過だけで**起こる（例: 外部 API が新しい必須パラメータを求めるようになり、コードを変えていないのに呼び出しが通らなくなる）。

運営者は1人なので、**判断はまとめて求め、承知の要らない読み取りは先に済ませてから報告する**。

## 週次（引数なし・数分で終わる。実物1周を回すと実費が出る）

上から順に実行し、**途中で失敗しても止めずに最後まで進める**（結果をまとめて報告するため）。

1. **状態確認**: 運営者向けの状態確認コマンド（または画面）があればそれを実行し、警告・異常の表示があれば原因を調べる。無ければ、公開先の主要画面と直近の定時処理の結果を開いて異常が無いか見る。
   （本番の異常を運営者へ通知する仕組み〔メール等〕があれば、その通知も確認する。）
2. **外部APIの受理確認**: 変更影響表（`.claude/rules/docdd-kit.md`「変更影響 → 必須の検証」）の『外部 AI／外部 API の呼び出し・プロンプト・出力の形』行にある**受理されるかの検査**を回す（実費ほぼ0円）。落ちたら**その日の変更ではなく provider 側の仕様変更**を疑い、公式ドキュメントで該当箇所を確認する。
3. **実物1周**: 同じ行の**実物で1周**（実APIで成果物まで見る検査）。`CLAUDE.md`「検証コマンド」表の『実物1周の費用上限』行に従う。
   - 未記入なら**実行しない**。報告に「『実物1周の費用上限』が未記入のため実物1周を実行しなかった」と書く。
   - 記入済みなら、実費の目安（1周あたりの金額と回数）を運営者に伝え、**承知を得てから**回す（必要ならローカルでアプリを起動する）。上限を超えそうになったら止めて報告する。
   - 回したら、AI・外部APIの成果物と、報告に出る成果物の形（例: 文字数・書式・リンクの有無など、そのアプリで決めている成果物の形）を目で見る。
4. **依存の脆弱性**: `CLAUDE.md`「検証コマンド」表の『依存の脆弱性』行を実行する。新しい high/critical が出ていたら、据え置く前に**上げられるか**を試す（例: npm なら `overrides` で入れ子の依存の版も寄せられることがある）。critical は据え置かない（上げられなければ、運営者にすぐ伝える）。
   - 終了コードだけで深刻度を決めない。出力の深刻度も見る（例: yarn v1 の `yarn audit` は、high 未満の脆弱性だけでも終了コードが 0 以外になる）。
   - **行が `node scripts/audit-check.mjs`（npm）のとき**: 据え置きは `scripts/audit-allowlist.json` に、脆弱性の ID の単位で書く。
     ```json
     { "<パッケージ名>": { "ids": ["GHSA-xxxx-xxxx-xxxx"], "why": "<なぜ今直さないか>", "until": "YYYY-MM-DD" } }
     ```
     - ID（`GHSA-` で始まる番号）は audit-check の出力から写す。`why` は運営者が読める日本語で書く（例: 本番で通る経路が無い・直った版がまだ出ていない）。`ids`（1 件以上）・`why`・`until` のどれかが欠けると、audit-check は書き方の誤りとして止まる（終了コード 2）。
     - 同じパッケージでも、`ids` に無い脆弱性が出たら落ちる。ID を足す前に、その脆弱性ごとに上げられるかを試す。
     - 合格したときに audit-check が出す、据え置き中の ID を報告に写す。
     - 期限（`until`）を過ぎると落ちる。今週中に上げるか、期限を延ばす理由を書く（延ばすなら `until` を新しい日付にし、理由を `why` に書く）。
   - **npm 以外（pnpm・yarn・bun・Python など）のとき**: これらのコマンドは `scripts/audit-allowlist.json` を読まない。据え置くなら、`tasks/BACKLOG.md`「要決定・外部準備（ユーザー作業）」に `**D-<番号>: <パッケージ名> の脆弱性を据え置く**` として、ID・理由・期限を書く（書式は `tasks/BACKLOG.md` 運用ルールの見本。`- 状態: 未決` の行を含む）。据え置いている間、『依存の脆弱性』行は落ちたままになる。毎週、出た ID が要決定に書いた ID だけかを突き合わせる（決まった据え置きはアーカイブへ移るので、`tasks/BACKLOG.md` と `tasks/archive/BACKLOG-done.md` の両方を ID で検索する）。書いていない ID は新しい脆弱性として扱い、期限を過ぎた据え置きは上の期限切れと同じに扱う。
5. **溜まったデータ**: テストで作ったユーザー・送信待ちのまま残った通知など、溜まりやすいデータの**件数**を見る。掃除するコマンドがあれば **dry-run（消さずに対象だけ数える実行）の結果を報告するところまで**にする。削除の適用は、運営者の指示があるときか、`/docdd:add-task` で起票したタスクとして行う。掃除の仕組みが無く溜まっているなら、件数を報告し `/docdd:add-task` で起票する。
6. **未pushの確認**: `git branch -vv` で未pushコミット数を見る。溜めすぎない。
7. **控えの鮮度**: `CLAUDE.md`「反映コマンド」表の『本番 DB のバックアップ』行を見る。「自動（DB サービス側）」なら、行に書いてある戻せる範囲を報告に写して終わり。**コマンドが書いてあるとき**は、`/docdd:release` が控えを取るのは **migration を含む反映のときだけ**なので、反映が間遠だと控えも古くなる。`git fetch --quiet` のあと `git log --since="1 month ago" --first-parent -m --name-only origin/<本番ブランチ>` に migration が出るかを見る（merge で取り込んだものは取り込んだ日に数える。置き場の見分け方は `${CLAUDE_PLUGIN_ROOT}/skills/release/SKILL.md` の §0 手順10 を Read で読んで従う。release は手動専用なので Skill では読めない）。出れば、そのときに取れているので終わり。出なければ **直近 1 か月は `/docdd:release` が控えを取っていない（migration を含む反映が無い）**と報告し、次の要決定を 1 回だけ積む（番号はアーカイブも含めた既存の D-番号の次。`grep -n "控えを取る間隔" tasks/BACKLOG.md tasks/archive/BACKLOG-done.md` に既にあれば積まず、決まった内容に従う）。

   **D-<番号>: 反映が間遠なときに控えを取る間隔** — migration を含む反映が無い月も本番 DB の控えを取るか。
   - 状態: 未決
   - 案A（推奨）: 『本番 DB のバックアップ』行を「自動（DB サービス側）: <戻せる範囲>」に変える。以後この手順は行の内容を報告に写すだけになる
   - 案B: 月に 1 回、点検のときに行のコマンドで取る（取る前に運営者の承知を得る。取り方と確かめ方は `${CLAUDE_PLUGIN_ROOT}/skills/release/SKILL.md`「共通の手順」の『本番 DB のバックアップを取る』を Read で読んで従う。中身は開かない）
   - 案C: 取らない（migration を含む反映のときだけでよい）

**報告に含める**: 状態確認で出た警告・異常、受理確認と実物1周の結果と実費（回さなかったらその理由）、audit の増減・据え置き中の ID・期限切れの据え置き、溜まったデータの件数と dry-run の結果、控えの鮮度（「自動」なら戻せる範囲、コマンドなら直近 1 か月に migration を含む反映があったか。この場で取ったならその日時と大きさ）、未pushコミット数、**運営者に決めてほしいこと**（承知待ちの操作を含む）。

## 月次（`/docdd:maintenance monthly`・週次 1〜7 に追加して実行。番号は週次と別に数える）

7. **費用の実績**: 当月と前月の外部APIの利用記録（従量課金の実績を記録しているテーブル・画面）を provider 別に集計し、想定と比べる。増えていれば原因（呼び出し回数の内訳。用途別・provider 別など）を分解して示す。
8. **バックアップの復元テスト**: `docs/operations/backup-and-restore.md` §3（データを戻す。自前の文書ならデータを戻す手順を書いた節）のとおり、**本番以外の DB（保存データ）へ戻すところまで**試す。取れているだけでは戻せるとは言えない。控えの取り方は `CLAUDE.md`「反映コマンド」表の『本番 DB のバックアップ』行にある（「自動（DB サービス側）」なら、サービスの画面から復元用の控えを取り出す）。その行が未記入か「無い」なら、復元テストの前に取る手段を決めるよう報告で伝える。同文書の §2（置き場所）か §3（データを戻す）が空で試せないなら、それを埋めることを `/docdd:add-task` で起票する（この場で手順を書き起こさない）。試したら結果を同 §5 の表へ 1 行足し、そのファイルだけを `git add` してコミットする（点検結果の記録なので、修理には当たらない）。
9. **外部APIの変更確認**: 使っている外部API（AI provider・連携先サービス・決済サービスなど）の変更履歴を確認し、`docs/` で外部APIの仕様に依存すると記した箇所（「実装時に要確認」などの注記）と突き合わせる。破壊的変更があれば `/docdd:add-task` で起票する。
10. **古いデータの確認**: 定時処理の実行記録・外部取得の結果・通知など、保持期限を決めているデータの保持が効いているかを件数で見る。増え続けていたら cleanup が動いていない。

## ルール

- **実費が出る手順（3）は、実行前に金額の目安を伝え、運営者の承知を得てから実行する。** 『実物1周の費用上限』行が未記入なら実行しない。（月次7「費用の実績」は記録の集計なので実費は出ない）
- 外部へ副作用を出す操作（外部サービスへの実投稿・実課金・第三者へのメール）はしない。点検は読み取りと非productionに限る（**本番データの削除・更新を含む操作はしない**。必要なら運営者の指示を待つか `/docdd:add-task` で起票する）。例外は週次7「控えの鮮度」で案B が決まっているときの控えの取得だけで、これは本番データを変えないが、実行前に運営者の承知を得る。
- この場で直してよいのは、依存の版上げと、据え置きの更新（npm は `scripts/audit-allowlist.json` の `ids`・`why`・`until`。npm 以外は `tasks/BACKLOG.md` の要決定に書いた据え置き）だけ。直したら変更影響表の該当行を回し、パスを明示して `git add` してコミットする。
- それ以外の見つけた不具合は `/docdd:add-task` で起票する（この場で実装しない。点検と修理を混ぜると、点検が終わらない）。仕様判断が要るものは `tasks/BACKLOG.md` の「要決定・外部準備（ユーザー作業）」へ追記して先へ進む。
- 定期実行するなら `/loop /docdd:maintenance`（セッション中）またはクラウドスケジュール（`/schedule`）で週1回にする。無人で動くときは、実物1周（3）と、承知や指示が要る操作を行わず、報告に「承知待ち」として残す。

## なぜこれが必要か

`docs/operations/development-and-testing.md` §1（テストの層と、それぞれ見えないもの。自前の文書ならテストの層を書いた節）のテストの層はすべて**変更起点**で走る。時間がたつだけで変わる次の5つは、どの層も見ない。

| 時間がたつと変わるもの | 見る手順（数字は週次、「月次」付きは月次） |
|---|---|
| 外部APIの仕様変更（必須パラメータの追加など） | 2・3・月次9「外部APIの変更確認」 |
| 新しい脆弱性の公表 | 4 |
| データの滞留（送信待ちの通知・テストユーザー） | 5・月次10「古いデータの確認」 |
| 控えの古さ（本番 DB のバックアップ） | 7・月次8「バックアップの復元テスト」 |
| 費用の増加 | 1（状態確認に当月費用が出るならそれ）・月次7「費用の実績」 |

# speed-up の落とし穴

速くする変更で起きやすい失敗を「症状 → 見る場所 → 対策」で並べる。`/docdd:speed-up` で境界・事前描画・キャッシュ・全リクエストを通る層に触る前に読む。

| 症状 | 見る場所 | 対策 |
|---|---|---|
| 共通のナビゲーションなどをクライアント側で動く部品に変えたら、その部品を使う全画面が実行時エラーになる。型検査は緑のまま | 変えた部品が関数を props で受け取っていないか（関数はサーバー／クライアントの境界を越えられない） | 部品を丸ごとクライアント側にしない。動く部分だけを小さな部品に切り出す。境界を動かしたら必ず実ブラウザ（E2E か `/docdd:playwright-cli`）で確かめる |
| 静的化・事前描画（prerender・ISR など）にしたら、HTTP は 200 のまま画面の script が1本も動かない | nonce ベースの CSP を使っているか。`docs/decisions/` の ADR と `docs/requirements/` に「全ルートを動的描画にしている」理由が書かれていないか | nonce ベースの CSP と静的な事前描画は両立しないことがある。その場合は事前描画へ寄せる提案をしない。触れたら `AGENTS.md`「検証コマンド」表の『ビルド』行 ＋ 実ブラウザでコンソールエラーまで見る |
| 解約したのに使える／契約したのに使えない／編集した内容が戻る | リクエストを跨ぐキャッシュ（フレームワークのデータキャッシュ・再検証つきキャッシュ）に、契約・利用上限（残量）・利用者が編集中のデータを載せていないか | リクエスト内メモ化はリクエスト内だけに使う。これらの値はリクエストを跨いでキャッシュしない（関門の表） |
| 1つ処理を足しただけで全画面が遅くなる | 全リクエストを通る層（例: middleware）に DB 読み取りや外部 HTTP を足していないか | この層には処理を足さない。逆にここの往復を削ると効果が最も大きい |
| 開発サーバーで測ると、改善したはずの数字が前と区別できない | 計測を開発サーバーで行っていないか | `AGENTS.md`「検証コマンド」表の『ビルド』行と『本番モード起動』行で起動した本番モードで、3回測って中央値を比べる |

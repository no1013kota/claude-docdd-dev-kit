# security-audit の落とし穴

見落としやすい形を「症状 → 見る場所 → 対策」で並べる。`/docdd:security-audit` の §2・§3 に入る前に読む。

| 症状 | 見る場所 | 対策 |
|---|---|---|
| 監査を「緑」で終えたのに、公開入口・依存・ファイル保存・CSP が報告に1行も出てこない | 報告の骨子が §1 のコマンドの出力になっているか。§3 の12観点を少数のカテゴリにまとめていないか | 観点をまとめない。§1 の一覧を1行ずつ「見た／穴あり／範囲外」で埋め、見なかったものを名指しする |
| 一部の画面（ログイン画面など）だけ CSP やヘッダが効かず、HTTP は 200 のまま画面が壊れている | ヘッダ・CSP の適用先を決める設定（全リクエストを通る層の対象パス指定など）と、§1 で数え上げたページの一覧 | 適用先を手で列挙しない。コマンドで出したページ一覧と突き合わせ、ビルド ＋ 実ブラウザでコンソールエラーまで見る |
| 検出器のテストは緑なのに、秘密値や外部サービスの生エラーがログへ出る | テストのスタブ・モックが、実物のエラークラス（本文や鍵をプロパティに持つもの）と同じ形か。素の `Error` などで代用していないか | 実物のクラスを通すテストを1件足すか、スタブを実物と同じ形にする。「テストがある」ではなく「実物を通しているか」で判定する |
| 反証を飛ばした候補が報告に混ざり、本物の指摘まで信用されなくなる | 各候補に「どこの層で止まらないか」をコードで確かめた記録があるか | 反証していない候補は報告に出さない。可能なら実際に動かして再現する |

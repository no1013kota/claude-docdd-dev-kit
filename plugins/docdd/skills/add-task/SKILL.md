> **前提（docdd）**
> - 最初に `tasks/BACKLOG.md` と、`CLAUDE.md` の「検証コマンド」表があるかを確かめる。どちらかが無ければファイルを作らず、「先に `/docdd:init` を実行してください」と伝えて止まる。
> - `/docdd:init`・`/docdd:release`・`/docdd:update-kit` は運営者が自分で打つコマンドで、Claude のスキル一覧には出ない。一覧に無いことを不具合として伝えない。止まるときは要望の中身の検討を始めない。
> - `CLAUDE.md`「スキルへの追加指示」にこのスキルの行があれば、本文より優先する。

# add-task：要望や仕様書をタスクに変える

利用者の言葉（「〜したい」「〜が使いにくい」「〜が動かない」）や、利用者が書き換えた仕様書を、**着手できるタスク**として `tasks/BACKLOG.md` へ起票する。`/docdd:dev-loop` はここに起票されたものを実行する。

**このスキルは実装しない。** コードは 1 行も変えず、BACKLOG（と必要なら「要決定」）を更新する。docs で直すのは、B-6 で、タスクにならなかった書き換えをコミットするときの更新日と変更履歴だけ。

## どちらで進めるか

| 打ち方 | 進め方 |
|---|---|
| `/docdd:add-task <やりたいこと>` | **A. 要望から起票する**（1 件） |
| `/docdd:add-task`（何も書かない） | **B. 仕様書から起票する**（まとめて）。仕様書に書き換えも、まだタスクになっていない所も無ければ「何をしたいですか」と聞き、答えを A で起票する |
| `/docdd:add-task <docs/ の文書かフォルダ>`・`/docdd:add-task HEAD~N` | **B** を、その範囲に絞って行う |

- B になるのは、何も書かないときと、引数が `docs/` の文書・フォルダか git の範囲（`HEAD~3`・コミットの番号など）**だけ**のとき。文の中にパスが混ざるとき（例: 「`docs/requirements/06_screens.md` の S-02 で並び順が逆」）は A で進め、A-2 でその節と照合する。
- Claude が会話で受けた要望から呼ぶときは、要望を引数に渡す（A になる）。
- やりたいことの中身が「仕様書を書き換えたのでタスクにして」なら、何も書かなかったときと同じに B で進める。

## 共通の決まり

### タスクの書式

```markdown
### T-01: <タスク名> `todo`
- 参照: PRD A-1 / requirements/06_screens.md S-01 / 依存: なし / サイズ: S
- 完了条件:
  - <動作で確認できる形>
  - <異常系・空状態を 1 行>
- メモ: <なぜ必要か・注意点>
```

| 項目 | 決まり |
|---|---|
| ID | 既存の連番の次（節を分けているなら該当節の連番の次）。**アーカイブも含めた最大の次**にする（終えたタスクはアーカイブへ移っているので、BACKLOG だけを見ると番号が重なる。`grep -oE "^### T-[0-9]+" tasks/archive/BACKLOG-done.md`）。節の**新設はユーザーに確認してから** |
| 配置 | 該当節の末尾。優先度が高ければ節内で上げてよい（上ほど優先）。何を上に置くかは `tasks/BACKLOG.md`「運用ルール」の並べ替えの基準に従う（その箇条が無い古い BACKLOG なら「失敗が記録されず運営者に知らされない → 実害 → 保守性 → 見た目」の順） |
| 大きさ | **1 タスク = 1 コミットで完了できる大きさ。** S＝半日以内、M＝1日、L＝それ以上。画面追加・DB 変更・定時処理や外部 API 呼び出しの追加が同時に必要なら分ける。**L のまま起票するのは、分割すると途中状態で動かなくなる場合だけ** |
| 完了条件 | 「〜を改善する」ではなく「〜が表示される」「〜が保存される」。**`/docdd:dev-loop` がテストの根拠にする** |
| 参照 | 書き方は `tasks/BACKLOG.md` の運用ルールのとおり。機能は `PRD A-1 / requirements/<ファイル名> <見出しID>`（見出し ID は `docs/requirements/README.md` の決まり。S=画面、D=データ、P=処理、API=API。文書ごとに足した接頭辞（例: RULE-01）も使う）。requirements がまだ無ければ `PRD A-1（requirements は本タスクで追記）`。ID を付けない requirements の文書は `requirements/<ファイル名> <見出し>`。そのほかの仕様書は `<docs/ からのパス> <見出し>`（例: `specs/booking.md 予約の取り消し`）。基盤タスクは `docs/operations/development-and-testing.md §4`。「〜のあたり」のようにぼかして書かない。振る舞いを変えない改善（リファクタ）だけは例外で、`なし（振る舞いを変えない）` と書く |
| 参照先が無い | 存在しない `docs/requirements/` の文書を参照に書くなら、その文書を作ることを完了条件に 1 行入れる。参照がそもそも書けないなら仕様が無いということなので、正本の追記もタスクに含める |
| 依存 | 先に済んでいる必要があるタスク ID と要決定の D-番号。無ければ `なし`。「アプリの土台を作る」が `done` でなければ、機能タスクの依存にその ID を書く |
| テスト基盤のタスク | タイトルは「テスト基盤の導入」で始める（E2E だけなら「テスト基盤の導入（E2E）」。ほかのスキルはこの書き出しで見つける）。完了条件に「単体の見本テスト 1 件が緑」「画面があるなら E2E（実際に動かす）の見本テストも 1 件が緑」「`CLAUDE.md`「検証コマンド」表の該当行が埋まる」を入れる（E2E だけなら単体の行は省く） |

**技術選定（フレームワーク・DB・テスト基盤・主要なライブラリ）が要るものは分ける。** 先に「ADR 案を書く」S タスク（完了条件: `docs/decisions/` に案と推奨を書き、運営者が承知する）を起票し、実装タスクの依存にその ID を書く。依存するパッケージは承知の後に入れる。「テスト基盤の導入」は `docs/operations/development-and-testing.md` §4 に推奨があるので分けない（`/docdd:dev-loop` が着手時に 1 回確認する）。

### 判断が要るものは「要決定」へ

費用・外部サービスの契約・法務・スコープの広がり・後から変えにくい利用者に見える選択（料金の見せ方・公開範囲など）は**勝手に決めない**。`## 要決定・外部準備（ユーザー作業）` へ次の書式で追記し、**可能なら案A/案Bと推奨**を添える。番号はアーカイブも含めた既存の D-番号の次。

```markdown
**D-1: <論点>** — <背景 1〜2 文>
- 状態: 未決
- 案A（推奨）: <内容と、選んだときのデメリット>
- 案B: <内容と、選んだときのデメリット>
```

決まったら「状態」を `決定（YYYY-MM-DD, 案A）→ 書き戻し先: PRD §4 ／ ADR-0001` の形に書き換える（`/docdd:dev-loop` が行う）。

- (a) 案が分かれる要決定は、**推奨案を前提にしたタスクだけ**を起票する。他の案のためのタスクは起票しない。
- (b) 要決定で塞がれるのがタスク本体だけなら、本体を `todo` で起票し、依存に D-番号を書く。土台のタスクを別に立てるのは、本体と 1 コミットで完了できないときだけ。
- (c) 費用・契約を伴わない仕様の選択（確認メールを送るかどうか、など）は要決定にしない。推奨案をメモに書いて進める。

## A. 要望から起票する

### A-0. 重複を先に潰す（必須）

`git log --oneline -15` と `tasks/BACKLOG.md` を読む。**既に `todo`／`doing`／`done`／`blocked` にある要望を二重に起票しない。** 同じものがあれば起票せず、そのタスクIDを案内して終わる。`dropped`（取り下げ）にあれば、取り下げた理由を示し、起票し直すかを聞く。

- まだ動いているもの（`todo`／`doing`／`blocked` と未決の要決定）は `tasks/BACKLOG.md` にある。そのまま読む。
- 終えたもの（`done`／`dropped`）と決まった要決定は `tasks/archive/BACKLOG-done.md` にある。**丸ごと読まず、要望の言葉で検索する**（言い換えも含めて 2〜3 語。当たった見出しの前後だけを読む。ファイルが無ければ飛ばす）:

  ```bash
  grep -nE "^### .*(通知|メール)" tasks/archive/BACKLOG-done.md   # タスクの見出しから探す
  grep -n "通知" tasks/archive/BACKLOG-done.md | head -20           # 本文・メモまで探す
  ```

要望がテスト基盤の導入のとき（「テスト基盤の導入（E2E）」も含む）は、次のとおりにする。

- タイトルが「テスト基盤の導入」で始まり、状態が `done`・`dropped` 以外のタスクがあれば、新しく起票しない。その ID を示す。
- 要望と比べてそのタスクに足りない完了条件（例: E2E（実際に動かす）の見本テスト 1 件が緑、『E2E（実際に動かす）』行が埋まる）があれば、追記してよいかを運営者に聞く。承知を得たら、そのタスクの完了条件だけを追記し、`git add tasks/BACKLOG.md` だけを行って `chore(backlog): T-xx に完了条件を追記` でコミットして終わる。
- 「テスト基盤の導入」で始まるタスクが `done`・`dropped` のものしか無ければ（アーカイブも検索する）、上の確認に従う（中身が違えば起票する）。

### A-1. 要望を1文にする

「**誰が・どの画面（ゲームならシーン・モード）で・何ができるようになるか**」の形にする。読み取れない情報は推測で埋めず、**着手に必要な最小限だけ**質問する（デザインの細部・将来の拡張は聞かない）。

### A-2. 正本と照合する（この順）

| 確認 | 該当したら |
|---|---|
| 基盤・環境タスク（テスト基盤・CI・ローカル DB）か | PRD との照合は免除する。参照は `docs/operations/development-and-testing.md` の該当節（テスト基盤なら §4）にする |
| `docs/PRD.md` §3.2「やらないこと」（雛形の場合。自前の PRD なら「やらないこと」相当の節）に該当するか | **起票せず終わる。** スコープ外である旨と、進めるならPRD改定が必要であることを伝える |
| どの機能（`docs/PRD.md` §3.1 の機能一覧。雛形の場合。自前の PRD なら「機能一覧」相当の節）・画面・処理（`docs/requirements/` の該当節）・そのほか `docs/` に置いた仕様書の節に紐づくか | 紐づく正本が無い＝**新しい仕様**。PRD・`docs/requirements/`・そのほかの仕様書のどれかの改定をタスクに含める |
| 既存の実装で既に満たせているか | 使い方を案内して終わる |

### A-3. 起票する

「共通の決まり」の書式で、1 件（分ける決まりに当たるときは、分けた数だけ）を `## タスク` 節へ書く。判断が要るものは「要決定」へ。

- 不具合なら、「再現手順」「実際に起きたこと」「期待する動作」を完了条件へ落とす。原因が分かっていればメモへ書く。**原因不明のまま「調査する」だけのタスクにしない**（調査は `/docdd:dev-loop` の中で行う）。
- 1 回で起票するのは**関連する 1 つの要望**まで。複数言われたら分けて起票し、それぞれ独立して着手できる形にする。

### A-4. コミットと報告

- `git add tasks/BACKLOG.md` のようにパスを明示し、BACKLOG だけを stage する（要決定も同じファイルにある）。`git status` でコードが変わっていないこと、無関係な変更を巻き込んでいないことを確かめる
- メッセージ: `chore(backlog): <要望の要約>を起票`
- 報告: タスクID／サイズ／完了条件の要点／新たな要決定／**次に実行するコマンド**（`/docdd:dev-loop <ID>`）
- 新たな要決定があれば、報告に「要決定は D-番号ごとに『A』『B』で答えればよい（例「D-1 は A、D-2 は B」）。全部推奨でよければ『推奨で』」と書く

## B. 仕様書から起票する

`docs/` の仕様書を読み、**まだタスクになっていない所**と**書き換えた所**をタスクに下書きして、運営者に見せる。**承認を得てから** `tasks/BACKLOG.md` へ書く。

### B-1. 範囲を決める

| 引数・状態 | 読む範囲 |
|---|---|
| 引数に文書かフォルダ（例: `docs/requirements/`） | その中の仕様書 |
| 引数に git の範囲（例: `HEAD~3`） | その範囲で変わった仕様書の、変わった節（`git diff <引数> -- docs`） |
| 引数が無く、仕様書（下の表の文書）に未コミットの変更がある（`git status --porcelain -- docs` から、読まない文書を除いて見る） | 変わった仕様書の、変わった節（`git diff HEAD -- docs`。未追跡の文書は全体） |
| 引数が無く、仕様書に未コミットの変更が無い | 仕様書の全体 |

仕様書として読む文書:

| 文書 | 読む単位 |
|---|---|
| `docs/PRD.md` | 機能一覧（§3.1。自前の PRD なら「機能一覧」相当の節）の行。A-番号で指す |
| `docs/requirements/` の各文書 | 見出し ID の付いた節（`S-01` など。決まりは `docs/requirements/README.md`）。ID を付けない文書は、見出しの節 |
| そのほか `docs/` に置いた仕様書 | 見出しの付いた節。見出しで指す |

次は仕様書として読まない: `docs/README.md`・`docs/operations/`・`docs/decisions/`（ADR）・`docs/_imported/`（取り込んだ原文。中身を PRD へ移してから使う）・`docs/requirements/README.md`・`docs/requirements/00_template.md`。ADR の決めたことを作業にするなら、A で 1 件ずつ起票する。

### B-2. 読む

- `docs/README.md`（どの文書が何を定義するか）と、B-1 の範囲の仕様書。
- `docs/PRD.md` の「やらないこと」（§3.2。自前の PRD なら相当の節）。範囲に PRD が無くても読む。
- `tasks/BACKLOG.md` 全体。既にあるタスク（状態を問わない）の「参照:」と、いちばん大きい T-番号・D-番号を控える。終えたタスクと決まった要決定は `tasks/archive/BACKLOG-done.md` にある（あれば）。**丸ごと読まず**、番号は `grep -oE "^(### T-[0-9]+|\*\*D-[0-9]+)" tasks/archive/BACKLOG-done.md` で拾い、同じものがあるかは A-番号・見出し ID・機能名で検索する。
- `git log --oneline -15`。
- 範囲に中身のある仕様が 1 つも無ければ（全部 `{{…}}` のまま、など）、何も書かない。引数が無ければ「何をしたいですか」と聞き、答えを A で起票する。引数で範囲を絞っていたら止まり、「その範囲に中身のある仕様がありません。仕様書を書くか、`/docdd:add-task <やりたいこと>` で起票してください」と伝える。

### B-3. 仕分ける

PRD の行と requirements の節が同じ機能を書いているなら、1 件にまとめて参照に両方を書く。

| 状態 | 扱い |
|---|---|
| 書き換えた所で、その節を参照する `done` のタスクがある | 「<A-番号・見出し ID・見出し> の変更を反映する」タスクを下書きする。メモに、何がどう変わったかを書く |
| まだどのタスクも参照していない | 下書きの対象。ただし、画面の名前・API のパス・処理の名前でコードを検索して、既にあるように見えるなら起票しない（報告に「実装済みに見える: <ファイル>」と書く）。書き換えた所で、コードが書き換える前の内容のままに見えるなら、上の行と同じ「変更を反映する」タスクを下書きする |
| `done` のタスクが参照していて、書き換えた所ではない | 起票しない（実装済み） |
| `todo`・`doing` のタスクが既に参照している | 起票しない。報告に「既存: T-xx」と書く。書き換えた所なら、そのタスクの完了条件を見直すよう報告に書く |
| アーカイブの `dropped` のタスクが参照している | 起票しない。報告に「取り下げ済み: T-xx」と、取り下げた理由を書く |
| `{{…}}` のまま（未記入） | タスクにしない。要決定 D-番号（論点「<A-番号・見出し ID・見出し> の中身を決める」）に回す |
| 判断が要る（費用・外部サービスの契約・法務・公開範囲など） | 論点を要決定 D-番号に回す。タスクは起票し、依存にその D-番号を書く |
| PRD の「やらないこと」と食い違う | 起票しない。報告で食い違いとして伝える |
| PRD の行で、優先度が Must 以外 | 今回は扱わない。報告に件数だけ書く |

### B-4. 下書きを表で見せる（まだ書き込まない）

下書きが 0 件なら表を出さず、起票しなかったものと理由を報告する。引数が無ければ「何をしたいですか」と聞き、答えを A で起票する。

表の例:

| ID | タスク名 | 参照 | サイズ | 完了条件の下書き（正常系 1・異常系 1） | 依存 |
|---|---|---|---|---|---|
| T-03 | 予約を一覧で見られる | PRD A-1（requirements は本タスクで追記） | M | 正常: 自分の予約が日付順に表示される／異常: 予約が 0 件なら「予約はまだありません」と表示される | T-01 |

- ID・大きさ・参照・依存は「共通の決まり」のとおり。「テスト基盤の導入」「アプリの土台を作る」が既にあれば、その番号に続ける（T-01 から振り直さない）。L になるものは、2〜3 件の S・M に分けた案を示す。
- **上限 7 件。** 8 件目以降は起票せず、報告に「次に起票する候補」として並べる。
- 表の下に、新しく作る要決定（D-番号・論点・案A（推奨）・案B）を並べる。
- 最後に「この内容で起票してよいですか。直したい行は ID で指示してください」と 1 回だけ聞く。

### B-5. 承認後に BACKLOG へ書く

- 書く直前に `tasks/BACKLOG.md` を読み直し、同じものが増えていれば、その行は起票しない。
- 承認されなかった行は書かない。直す指示があった行は、直してから書く。
- タスクは `## タスク` 節の末尾へ、「共通の決まり」の書式で書く（完了条件は下書きの 2 行。メモには仕様書の行・節の要点を写す）。要決定は「要決定・外部準備」へ。

### B-6. コミットと報告

- `git add tasks/BACKLOG.md` だけを行う（タスクも要決定もこのファイルにある）。`git status` で、ほかのファイルを stage していないことを確かめる。docs の未コミットの変更のうち、タスクになったものは、このコミットに含めない（そのタスクを進める `/docdd:dev-loop` のコミットに入る）。
- タスクにならなかった書き換え（表記の修正・Must 以外の行・実装済みに見える所・やらないことと食い違う所など）だけの文書が残るなら、その文書を報告に並べ、「この書き換えをコミットしてよいか」を 1 回聞く（タスクになった書き換えも含む文書は、ここではコミットしない。そのタスクの `/docdd:dev-loop` がまとめてコミットする）。承知を得たら、その文書の冒頭の「更新日」を今日にし（仕様が変わったなら変更履歴に 1 行）、`CLAUDE.md`「検証コマンド」表の『docs の検査』『未記入欄の検査』行を回す（『docs の検査』が落ちたら、コミットせずに報告する）。通ったら、その文書だけを `git add` して `docs: 仕様書を直す` でコミットする。承知が無ければ残す（`/docdd:release` は、コミットしていない変更があると止まる）。
- メッセージ: `chore(backlog): 仕様書からタスクを起票`
- 報告:
  - 読んだ範囲（B-1 のどれか）
  - 起票したタスク（ID・タスク名・サイズ）
  - 新たな要決定。「D-番号ごとに『A』『B』で答えればよい。全部推奨でよければ『推奨で』」と添える
  - 起票しなかったものと理由（未記入・既存・取り下げ済み・実装済みに見える・上限超え・Must 以外・やらないことと食い違う）
  - 次の一手: `/docdd:dev-loop T-xx`（依存がすべて済んでいる、いちばん上の `todo` の ID）

## ルール

- **実装しない。**「ついでに直す」もしない。コードを変えたくなったらそれは `/docdd:dev-loop` の仕事。
- **推測で仕様を作らない。** 判断が要るものは要決定へ回し、暫定案を添える。仕様書に無い機能を B で足さない。
- **B では、承認の前に BACKLOG を書き換えない。**
- タスク名・完了条件・メモは日本語で書く。

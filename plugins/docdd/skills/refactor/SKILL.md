> **前提（docdd）**
> - 最初に `tasks/BACKLOG.md` と、`CLAUDE.md` の「検証コマンド」表があるかを確かめる。どちらかが無ければファイルを作らず、「先に `/docdd:init` を実行してください」と伝えて止まる。
> - `/docdd:init`・`/docdd:release`・`/docdd:update-kit` は運営者が自分で打つコマンドで、Claude のスキル一覧には出ない。一覧に無いことを不具合として伝えない。止まるときは要望の中身の検討を始めない。
> - 表の場所: 「検証コマンド」「反映コマンド」「スキルへの追加指示」は `CLAUDE.md`、「変更影響 → 必須の検証」・Definition of Done・規約は `.claude/rules/docdd-kit.md`（v0.1 系で導入したプロジェクトでは全部 `CLAUDE.md` にある。`/docdd:update-kit` で移せる）。
> - `CLAUDE.md`「スキルへの追加指示」にこのスキルの行があれば、本文より優先する。
> - 表の値が「無い」の行は飛ばし、二重波かっこ（`{{…}}`）のままの行は未記入として実行しない。どちらも理由を報告する（黙って省略しない）。
> - 課金・AI・ジョブ・決済など、このプロジェクトに無い機能についての手順は飛ばして「該当なし」と報告する。要決定には積まない。

# refactor：システム全体の安全なリファクタリング

外部から見た振る舞い・仕様・公開API/契約を変えずに、内部品質（重複・複雑度・境界・型・命名・デッドコード・テスト容易性）を上げる。**全体を一度に書き換えない。** dev-loop と同様バックログ駆動で、1回の実行で扱うのは1単位のみ（WIP=1）。仕様変更を伴うものはリファクタではないので dev-loop 側で扱う。

## 大原則（必ず守る）

1. **振る舞い保存**: 外部挙動・DB/APIの契約・画面仕様・プロンプト出力・エラー契約・エンジンが保存する値と参照（例: Unity のシリアライズされた値・.meta の GUID）を変えない。変わるならリファクタではない＝中止してユーザーに報告する。
2. **テストが安全網**: 単体テストが無ければ始めない（手順1）。着手前に `CLAUDE.md`「検証コマンド」表の『単体・DBテスト』行が緑であることを確認する。対象の挙動を守るテストが薄い箇所は、**先に特性テスト（今の挙動をそのまま記録するテスト）を別コミットで追加**してからリファクタする。
3. **小さく・可逆に**: 1単位＝1つの一貫した変更。無関係な変更を混ぜない。単位ごとに検証し、緑にできなければ直すか revert する。
4. **仕様の正本を守る**: docs/ が参照する構造（ファイル名・公開関数・型名・DBテーブル等）を変えたら /docdd:doc-sync で追随する。表現しきれない横断的判断は docs/decisions/ に ADR を残す。
5. **規約・秘密情報**: 規約（`.claude/rules/docdd-kit.md`）に従う。実キーを混入しない。`git add -A` を使わず、`git status` で無関係な変更の巻き込みを防ぐ。

## 手順

1. **緑を確認（テスト基盤の門）**: `git log --oneline -15` と `tasks/BACKLOG.md` を読み、`CLAUDE.md`「検証コマンド」表を見る。
   - 『単体・DBテスト』行が「無い」または未記入なら**着手しない**。`tasks/BACKLOG.md` に、タイトルが「テスト基盤の導入」で始まり状態が `done`・`dropped` 以外のタスクがあれば報告に「テスト基盤が無いため安全に行えない。T-xx を先に（`/docdd:dev-loop T-xx`）」、無ければ「テスト基盤が無いため安全に行えない。`/docdd:add-task テスト基盤の導入` を先に」と書いて停止する（導入の仕方は `docs/operations/development-and-testing.md` §4（テスト基盤が無いとき））。ただし `--audit`（監査のみ）はこの条件でも手順2〜3まで実行してよい。
   - 『単体・DBテスト』行を実行し、緑でなければ報告して着手しない。実行件数も見て、0 件なら緑にしない（例: Unity はテストが 0 件でも終了コード 0 で終わる。`-testResults` の XML の `total` を見る）。
   - 『型検査』『lint』行は、「無い」・未記入なら飛ばしてよい（理由を報告する）。あれば回して緑を確かめる。
2. **監査**: `tasks/BACKLOG.md` に未着手（`todo`）のリファクタ単位があれば、まず各単位の `file:line` を開いて**まだ直っていないことを確かめる**。直っていたものは `done`（理由 1 行）にして `node scripts/backlog-archive.mjs` でアーカイブへ移す（スクリプトが無ければ移さずに進み、報告で `/docdd:update-kit` を案内する）。残った単位があれば、それを今回の候補にして新しい監査はしない。残らなければ対象範囲を「## リファクタの観点」で洗い、各候補に *file:line / 種類 / 期待効果 / リスク / 規模 / 影響するテスト* を付ける。**監査するときは、前の監査の結果を持ち越さずその場で取り直す**（結果をファイルに溜めると、何回ぶんもの監査が層になって、直したものが `todo` のまま残る）。前に取り下げた候補を出し直さないよう、アーカイブを言葉で検索して確かめる（例 `grep -n "リファクタ" tasks/archive/BACKLOG-done.md`。丸ごとは読まない）。
   - 監査の範囲が広いときはサブエージェントに領域ごとに分担させてよい。実行（手順 4 以降）は必ず 1 単位ずつ検証する。
3. **起票（要承認）**: 価値が高く低リスクな順に並べて運営者に見せ、**承認を得た単位だけ** `tasks/BACKLOG.md` の「## タスク」へ起票する（上にあるものほど優先）。**全体リファクタは着手前にこの一覧を提示して承認を得る。** 却下された候補は `dropped` と理由を付けて起票し、`node scripts/backlog-archive.mjs` でアーカイブへ移す（次の監査で同じ候補を出し直さないため。スクリプトが無ければ移さずに進む）。起票・状態変更をしたら `git add tasks/BACKLOG.md tasks/archive/BACKLOG-done.md` だけを行い、`chore(backlog): リファクタ候補を起票` でコミットする。振る舞いが変わる候補はリファクタではないので、暫定案つきで「要決定」へ積む。`--audit` は**起票せずに一覧を見せるだけ**でここで停止する（BACKLOG は変えない）。

   リファクタ単位の書式（`tasks/BACKLOG.md` の「## タスク」へ、この形で足す）:

   ```markdown
   ### T-NN: <同じ判定が 3 か所にある → 1 つにまとめる> `todo`
   - 参照: なし（振る舞いを変えない） / 依存: なし / サイズ: S
   - 完了条件:
     - 外部から見た振る舞い・契約・画面が変わらない（既存のテストが緑のまま）
     - <何が消えたかが file:line で分かる形>
   - メモ: 種別 <重複 / 命名 / 型 / 未使用 / テスト容易性 / 境界> ／ リスク <低 / 中 / 高>
   ```
4. **1単位を実行（WIP=1）**: 手順3 で起票したリファクタ単位のうち、いちばん上のものを 1 件選んで `doing` にする（機能タスクは選ばない）。テストが薄ければ特性テストを別コミットで先に足す。項目外へ広げない。
5. **検証**: 変更影響表（`.claude/rules/docdd-kit.md`「変更影響 → 必須の検証」）に従う。加えて**差分が外部挙動・契約・スナップショットを変えていないこと**。動く経路があれば実際に動かす。
6. **docs同期＋完了**: `/docdd:doc-sync`（影響なしなら理由付きで記録）。`tasks/BACKLOG.md` の該当タスクを `done` にし、「実装メモ:」「検証:」の 2 行を足してから `node scripts/backlog-archive.mjs` でアーカイブへ移す。関連ファイルだけをパスを明示して `git add` し、`refactor(<scope>): 概要` でコミットする。報告に実施内容・判断・検証結果・次候補・新たな要決定を書く。

## リファクタの観点（監査チェックリスト）

- **重複**: コピペされたロジック・定数・型の共通化（Single Source of Truth 化）。
- **複雑度**: 長大な関数・深い分岐の分割、早期return、責務分離。
- **境界・依存**: レイヤ違反（UIからDB直結等）、循環依存、サーバー／クライアント境界の乱れ（フレームワークにその区別があれば。例: サーバー専用のモジュールがクライアント側から import されている）。
- **型**（静的型のある言語なら）: `any` 相当の緩い型・不要なキャスト・非null断定の削減、判別可能ユニオン化、DB の列挙値とコード側の型のドリフト解消。
- **命名・一貫性**: 命名規約・ファイル配置・エラーハンドリング様式・レスポンス形の統一。
- **デッドコード**: 未使用の export・依存・フラグ・分岐の削除。**参照0件は機械的に洗える**——リポジトリ全体で識別子の出現が定義行だけの export を数える。消すときは次の2つに注意する。
  - **型だけ使われていることがある。** コンポーネントが未使用でも、同じファイルの型を誰かが import している。**型は置き場（型だけを集めたファイル）へ移す**——中身が消えた後もファイルが残る原因はこれ。
  - **検出器が消えたファイルを見張っていると、検査自体が落ちて何も守らなくなる。** 削除したら検出器の相手を実在するファイルへ寄せる。
- **テスト容易性**: 副作用の注入化（純粋関数への抽出）、薄い箇所への特性テスト追加。
- **パフォーマンス**（挙動を変えない範囲）: 明白なN+1・不要な再計算・重い同期処理の是正。

## やってはいけないこと

- 全体の一括書き換え・大規模な同時変更（必ず小単位へ分割する）。
- 外部挙動・DB/API契約・画面仕様・プロンプト出力の変更（それは機能変更＝ dev-loop で扱う）。
- 保存された値を持つフィールドの改名や、アセットの移動・改名を、エンジンの仕組みを使わずに行うこと（例: Unity では、フィールドを改名するときに `[FormerlySerializedAs("旧名")]` を付ける。アセットの移動・改名は Editor で行う。Unity の外で動かして .meta と離れると、そのアセットへの参照が切れる）。
- テスト基盤が無いまま、またはテストを緑にしないままのコミット、スナップショット・契約テストの安易な書き換え。
- 承認前の全体リファクタ着手、無関係な変更の混在、`git add -A`。
- PRD の「やらないこと」（スコープ外の宣言）に反する方向への「改善」。検出したら実装せずユーザーへ警告する。

## Definition of Done

- [ ] 着手前に『単体・DBテスト』行が緑だった（テスト基盤が無いときは着手せず、報告して止めた）
- [ ] 外部挙動を変えていない（テスト緑・契約/スナップショット不変を確認）
- [ ] `tasks/BACKLOG.md` へ起票した単位があれば、状態と「実装メモ:」「検証:」を更新し、`done` はアーカイブへ移した
- [ ] `refactor(<scope>): …` でコミットした
- [ ] ＋ Definition of Done（`.claude/rules/docdd-kit.md`）

# verify-integration：統合テスト

変更に関係する境界（DB・サーバー側の処理・外部 API など、部品どうしがつながる所）だけを選んで検証する。**単体テスト・E2E・外部 live（本物の外部サービスを使う確認）の代わりにはしない。**

## 手順

1. **守る契約を先に列挙する** — DB 制約／DB の権限（RLS〔行ごとのアクセス制限〕など）／API 契約／状態遷移／冪等性（同じ処理を2回しても結果が変わらないこと）／同時実行。無関係な変更はしない。
2. **テスト用 DB を確かめる** — `AGENTS.md`「検証コマンド」表の『テスト用 DB』行の値で分ける。未記入、または ①②③ のどれにも当たらない値なら、DB を使う手順は実行せず理由を報告して止まる。
   - **① ローカル**: 接続先がローカル（`127.0.0.1`・`localhost`・SQLite などの手元のファイル）のテスト用 DB であることを確かめる。reset・drop・truncate・破壊的 migration は、このローカルのテスト用 DB でだけ行う。DB の初期化（migration を全件クリーン適用し直す操作）はクリーン適用の確認が要るときだけ（利用者が明示していなければ承認を得る）。
   - **② ホスト型の開発専用**: `AGENTS.md` に「開発専用・破棄可能」（本番と別で、消してよい）と明記された接続先に限って使う。明記が無い、または本番らしい接続先なら止めて報告する。reset・drop・truncate（テーブルや列を消す migration を含む）はしない。それ以外の書き込みと migration の適用はしてよい。テストデータは実行ごとの一意 ID で作り、終わったら今回作った分だけ消す（失敗しても消すことを試み、残ったら ID 付きで報告）。
   - **③ DB 無し**: 変更影響表（`AGENTS.md`「変更影響 → 必須の検証」）の DB に関する行（DB のスキーマ・権限・migration、DB へ書く値の形式など）を「該当なし（テスト用 DB は DB 無し）」と報告して終える。
3. **前提を整える** — ① なら『テスト用 DB』行の起動コマンドで DB を起動し、起動していることを確かめる（DB 未接続のとき実 DB を使うテストを skip する仕組みだと、未起動でも緑に見える）。② なら接続先の設定が効いていて、テストが実際にその DB へつながることを確かめる（`.env` の中身は開かず、接続先の値を報告に書かない）。テストデータは一意 ID。
4. **対象テストを選ぶ** — 下表。`rg`（無ければ `grep -rn`）で対応する「実 DB を使うテスト」を探し、無ければ追加する。
5. **実行する** — `AGENTS.md`「検証コマンド」表の『単体・DBテスト』行を、変更に近いテストファイル1件から → 関連する境界群 → 共通基盤・schema・認証・DB の権限を変えたら全件で退行確認（実 DB を使うテストは、DB 未接続のとき skip ではなく fail する形で回す）。『単体・DBテスト』行が「無い」か未記入ならテスト基盤が無い。統合テストは未実施として報告し、`tasks/BACKLOG.md` の基盤導入タスク（タイトルが「テスト基盤の導入」で始まり、状態が `done`・`dropped` 以外のタスク）の ID を添える（無ければ `/docdd:add-task テスト基盤の導入` での起票を案内する。導入方法は `docs/operations/development-and-testing.md` §4（テスト基盤が無いとき））。
6. **完全性を見る** — pass 数だけでなく fail／skip／todo。**必須の「実 DB を使うテスト」が1件でも skip なら合格としない。**
7. **報告** — 環境（テスト用 DB が ①②③ のどれか）／検証した契約／結果／skip／② なら後片付けの結果（残った ID）／実物1周の実費（行ったとき）／未検証事項。

## 変更種別 → 見る契約

| 変更 | 契約 |
|---|---|
| migration / DB の権限（RLS など） | schema・seed（初期データ）・行レベルの権限・別ユーザー拒否・制約・**ロール権限（GRANT）** |
| サーバー側の処理（API など） | 認証・入力検証・所有権・Origin（呼び出し元の確認）・署名・DB 反映 |
| 定時処理 / ジョブ | 状態遷移・冪等・再試行・同時実行。DB をキューに使うなら lease（処理中の占有）・stale 回収・deadline も（該当するものだけ） |
| 課金・利用量 | Webhook 重複・イベント順序・契約状態・利用上限（残量）の原子的更新 |
| 外部 API・AI | モックで契約と記帳（live はしない。ただし下の「実物で1周」は別途必須） |

## 見落としやすい3点（症状と対策は `references/pitfalls.md`）

- **ロール権限（GRANT）を明示的に検査する。** 行レベルの権限は、テーブルレベルの権限があって初めて評価される。一般利用者ロールだけでなく、**サーバー側が使う特権ロール自身の権限**も見る。管理者権限で DB へ直結する経路はロール権限を回避してしまうので、DB クライアントライブラリ・API 経由の経路で確かめる。テーブル追加時は既定権限（新しく作ったテーブルに自動で付く権限）まで確認する。
- **注入した本番実装は無検証になりやすい。** 純粋関数のテストが充実していても、サーバー側の処理（API など）が渡す実 DB クエリ・外部呼び出しは覆えない。サーバー側の処理そのものを実 DB で叩くテストがあるかを確かめる（例: 認証のセッションだけモックし、DB クエリは実際に走らせる）。
- **外部 API との噛み合いは実物でしか分からない。** モックしたテストは「送ったリクエストが受理されるか」「返ってきたものを扱えるか」を検証しない。外部 AI／外部 API の呼び出し・プロンプト・出力の形・tool 定義に触れたら、変更影響表の該当行どおり **受理されるかの検査＋実物で1周**（実 API で成果物まで見る）の両方を行う。

## 実物で1周の費用

- 実物で1周は費用が出る。`AGENTS.md`「検証コマンド」表の『実物1周の費用上限』行に従う。
- その行が未記入（二重波かっこのまま）か「無い」なら、実物で1周は**実行しない**。「実物1周は未実施（費用上限が未記入）」と報告し、`AGENTS.md` の該当行を埋めるよう伝える。
- 実行するときは、上限を超える前に止めて報告する。**実費を必ず報告する。**

## ルール

- テストを通す目的で DB の権限（RLS など）・認可・署名検証・冪等 guard（二重実行の防止）を弱めない。
- 本番と、共有の検証環境へ書き込まない。書き込んでよいのは ① のローカルのテスト用 DB と、② の「開発専用・破棄可能」と明記された接続先だけ。実課金・外部サービスへの実送信（投稿・通知）・実メールをしない。
- 「合格」は必要な統合テストが全実行され、fail と必須 skip が 0 のときだけ。環境不足なら**単体成功と統合未実施を分けて**報告する。

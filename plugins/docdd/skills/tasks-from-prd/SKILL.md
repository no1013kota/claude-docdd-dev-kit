> **前提（docdd）**
> - 最初に `tasks/BACKLOG.md` と、`CLAUDE.md` の「検証コマンド」表があるかを確かめる。どちらかが無ければファイルを作らず、「先に `/docdd:init` を実行してください」と伝えて止まる。
> - `/docdd:init`・`/docdd:release`・`/docdd:update-kit` は運営者が自分で打つコマンドで、Claude のスキル一覧には出ない。一覧に無いことを不具合として伝えない。止まるときは要望の中身の検討を始めない。
> - `CLAUDE.md`「スキルへの追加指示」にこのスキルの行があれば、本文より優先する。

# tasks-from-prd：PRD から最初のタスクを起票する

`docs/PRD.md` の機能一覧を上から読み、最初のタスク群を下書きして運営者に見せる。**承認を得てから** `tasks/BACKLOG.md` へ書く。要望を 1 件だけ起票するなら `/docdd:add-task` を使う。

**このスキルは実装しない。** コードも PRD も変えず、BACKLOG（と「要決定」）だけを更新する。

## 手順

### 1. 読む

- `docs/PRD.md` の §3.1「やること（機能一覧）」と §3.2「やらないこと」（雛形の場合。自前の PRD なら「機能一覧」「やらないこと」相当の節）。
- `tasks/BACKLOG.md` 全体。既にあるタスク（状態を問わない）と、いちばん大きい T-番号・D-番号を控える。
- `git log --oneline -15`。
- 機能一覧が無い、または優先度が Must の行が 1 件も無ければ、何も書かずに止まる。PRD の機能一覧を埋めるか、`/docdd:add-task <やりたいこと>` で 1 件ずつ起票するよう伝える。

### 2. Must の行を上から仕分ける

| 行の状態 | 扱い |
|---|---|
| 優先度が Must で、機能名と説明が書いてある | 下書きの対象 |
| `{{…}}` のまま（未記入） | タスクにしない。要決定 D-番号（論点「A-番号 の中身を決める」）に回す |
| 判断が要る（費用・外部サービスの契約・法務・公開範囲など） | 論点を要決定 D-番号に回す。機能のタスクは起票し、依存にその D-番号を書く |
| `tasks/BACKLOG.md` に同じものがある | 起票しない。報告に「既存: T-xx」と書く |
| §3.2「やらないこと」と食い違う | 起票しない。報告で PRD の食い違いとして伝える |
| Must 以外 | 今回は扱わない。報告に件数だけ書く |

### 3. 下書きを表で見せる（まだ書き込まない）

表の例:

| ID | タスク名 | 参照 | サイズ | 完了条件の下書き（正常系 1・異常系 1） | 依存 |
|---|---|---|---|---|---|
| T-03 | 予約を一覧で見られる | PRD A-1（requirements は本タスクで追記） | M | 正常: 自分の予約が日付順に表示される／異常: 予約が 0 件なら「予約はまだありません」と表示される | T-01 |

- **ID** は BACKLOG のいちばん大きい T-番号の次から振る。「テスト基盤の導入」「アプリの土台を作る」が既にあれば、その番号に続ける（T-01 から振り直さない）。
- **上限 7 件。** 8 件目以降は起票せず、報告に「次に起票する候補」として並べる。
- **1 タスク = 1 コミットで完了できる大きさ**にする（目安は S＝半日以内、M＝1日）。L になる行は、2〜3 件の S・M に分けた案を示す。
- **参照** は `docs/requirements/` に該当節があれば `PRD A-1 / requirements/<ファイル名> <見出しID>`、無ければ `PRD A-1（requirements は本タスクで追記）`。
- 「アプリの土台を作る」が `done` でなければ、機能タスクの依存にその ID を書く。
- フレームワーク・DB などの技術選定を機能タスクに混ぜない。選定が要るなら「ADR 案を書く」S タスク（`docs/decisions/` に案と推奨を書き、運営者が承知したら完了）に分け、機能タスクの依存にその ID を書く。
- 表の下に、新しく作る要決定（D-番号・論点・案A（推奨）・案B）を並べる。
- 最後に「この内容で起票してよいですか。直したい行は ID で指示してください」と 1 回だけ聞く。

### 4. 承認後に BACKLOG へ書く

- 書く直前に `tasks/BACKLOG.md` を読み直し、同じものが増えていれば、その行は起票しない。
- 承認されなかった行は書かない。直す指示があった行は、直してから書く。
- タスクは `## タスク` 節の末尾へ、次の書式で書く（完了条件は下書きの 2 行。メモには PRD の行の説明を写す）。

```markdown
### T-01: <タスク名> `todo`
- 参照: PRD A-1 / requirements/06_screens.md S-01 / 依存: なし / サイズ: S
- 完了条件:
  - <動作で確認できる形>
  - <異常系・空状態を 1 行>
- メモ: <なぜ必要か・注意点>
```

- 要決定は `## 要決定・外部準備（ユーザー作業）` へ、次の書式で書く。

```markdown
**D-1: <論点>** — <背景 1〜2 文>
- 状態: 未決
- 案A（推奨）: <内容と、選んだときのデメリット>
- 案B: <内容と、選んだときのデメリット>
```

### 5. コミットと報告

- `git add tasks/BACKLOG.md` だけを行う（タスクも要決定もこのファイルにある）。`git status` で、ほかのファイルを stage していないことを確かめる。
- メッセージ: `chore(backlog): PRD から初期タスクを起票`
- 報告:
  - 起票したタスク（ID・タスク名・サイズ）
  - 新たな要決定。「D-番号ごとに『A』『B』で答えればよい。全部推奨でよければ『推奨で』」と添える
  - 起票しなかった行と理由（未記入・既存・上限超え・Must 以外・やらないことと食い違う）
  - 次の一手: `/docdd:dev-loop T-xx`（依存がすべて済んでいる、いちばん上の `todo` の ID）

## ルール

- **実装しない。** コード・`docs/PRD.md`・`docs/requirements/` は変えない。
- **承認の前に BACKLOG を書き換えない。**
- PRD に無い機能を推測で足さない。PRD に無い要望は `/docdd:add-task` で起票する。
- タスク名・完了条件・メモは日本語で書く。

> **前提（docdd）**
> - 最初に `tasks/BACKLOG.md` と、`CLAUDE.md` の「検証コマンド」表があるかを確かめる。どちらかが無ければファイルを作らず、「先に `/docdd:init` を実行してください」と伝えて止まる。
> - `/docdd:init`・`/docdd:release`・`/docdd:update-kit` は運営者が自分で打つコマンドで、Claude のスキル一覧には出ない。一覧に無いことを不具合として伝えない。止まるときは要望の中身の検討を始めない。
> - 表の場所: 「検証コマンド」「反映コマンド」「スキルへの追加指示」は `CLAUDE.md`、「変更影響 → 必須の検証」・Definition of Done・規約は `.claude/rules/docdd-kit.md`（v0.1 系で導入したプロジェクトでは全部 `CLAUDE.md` にある。`/docdd:update-kit` で移せる）。
> - `CLAUDE.md`「スキルへの追加指示」にこのスキルの行があれば、本文より優先する。
> - 表の値が「無い」の行は飛ばし、二重波かっこ（`{{…}}`）のままの行は未記入として実行しない。どちらも理由を報告する（黙って省略しない）。
> - 課金・AI・ジョブ・決済など、このプロジェクトに無い機能についての手順は飛ばして「該当なし」と報告する。要決定には積まない。

# verify-e2e：E2Eテスト

ユーザー操作から画面・サーバー・DB の結果までを検証する（E2E＝利用者と同じ操作で端から端まで通す確認）。**確認範囲を超えた合格を報告しない。**

`CLAUDE.md`「検証コマンド」表の『開発サーバー起動』行が「無い」プロジェクトは **Web 以外**（例: Unity・Godot のゲーム、ネイティブアプリ）として扱う。Web 以外ではブラウザ・開発サーバー・`/docdd:playwright-cli` を使わず、『E2E（実際に動かす）』行の自動テスト（例: Unity の PlayMode テスト）か、運営者に確かめてもらう手順で確かめる。

## 手順

1. **シナリオを決める** — タスク・docs・`git diff` から「開始状態 → 操作 → 期待する画面／DB・ジョブの最終状態」を書く（ゲームなら「シーン → 操作 → 期待する状態・見え方」）。変更に直結する最小シナリオ＋壊れやすい主要経路。
2. **基盤を選ぶ**
   - `CLAUDE.md`「検証コマンド」表の『E2E（実際に動かす）』行にコマンドがあれば、それ（リポジトリで管理している自動 E2E）を優先する。
   - その行が「無い」か未記入なら、自動 E2E は無い。**探索的確認**（シナリオどおりに操作して目で見る確認）を行い、「自動E2E合格」とは呼ばない。Web はブラウザで行う（下の 2 つ）。Web 以外は、運営者に確かめてもらう手順（開く場面・操作・期待する見え方）を示し、結果を聞き取る。あわせて `tasks/BACKLOG.md` で基盤導入タスク（タイトルが「テスト基盤の導入」で始まり、状態が `done`・`dropped` 以外のタスク）を探す。あれば、その ID を報告に添える（そのタスクの完了条件に E2E が無ければ、`/docdd:add-task テスト基盤の導入（E2E）` で E2E の完了条件の追記を提案できる）。無ければ `/docdd:add-task テスト基盤の導入（E2E）` での起票を案内する。導入方法は `docs/operations/development-and-testing.md` §4（テスト基盤が無いとき）。
   - Web の探索的確認でブラウザを動かす道具を確かめる: `playwright-cli --version` → 通らなければ `npx --no-install playwright cli --help`（出力に `playwright-cli` を含む行があれば `npx playwright cli` で代用。終了コードでは決めない。古い Playwright は、その行の無いヘルプを出して 0 で終わる）→ それも無ければ、インストールしてよいかを利用者に聞く（入れ方は `/docdd:playwright-cli` の「インストール」）。断られたら利用者に画面を操作してもらい、結果を聞き取ったことを報告に書く。
   - Web の探索的確認では `CLAUDE.md`「検証コマンド」表の『開発サーバー起動』行でサーバーを起動して開く（行が未記入なら、起動方法を推測で決めず理由を報告して止まる）。
   - Web 以外で『E2E（実際に動かす）』行のコマンドが動かせないとき（例: Unity は、Editor で同じプロジェクトを開いていると batchmode で開けない）は、Claude がエディタを閉じない。閉じてから回すかを運営者に 1 回聞き、閉じられなければ運営者に確かめてもらう手順を示して「探索的確認」と書く。
3. **安全を確認する** — 下表。1つでも外れたら止める。
4. **データを用意する** — 専用テストユーザー＋実行ごとの一意 ID。作成 ID を記録。DB 全体を reset せず、他者のデータに触らない。
5. **実行する**
   - Web: 表示だけでなく URL・入力・二重送信防止・エラー表示・最終状態。コンソールエラー・失敗したリクエスト・予期しないリダイレクトも見る。
   - Web 以外: 『E2E（実際に動かす）』行のコマンドを回す。エンジンの起動と読み込みで時間がかかるので、途中で打ち切られないよう時間の上限を長めに取るか、バックグラウンドで回して終わりを待つ。ログのエラー（コンパイルエラーなど）も見る。
   - 自動テストの合否は終了コードだけで決めない。結果（Web 以外は結果ファイル。例: Unity なら `-testResults` で指定した XML）の実行件数・失敗数・skip の数も見る。実行件数が 0 なら合格にしない（例: Unity はテストが 0 件でも終了コード 0 で終わる）。
6. **後片付け** — 今回作成分だけ削除。失敗時も試み、残ったら ID 付きで報告。
7. **報告** — 自動か探索的か（探索的なら基盤導入タスクの ID か起票の案内）／環境／シナリオ／結果（自動なら実行件数・失敗数）／証拠／未検証事項。運営者の確認がまだの項目は「運営者確認待ち」として、開く場面・操作・期待する見え方を添える。

## 安全な既定（起動前に確かめる。テストの前処理などで自動で確かめる仕組みが無ければ、実行前に手で確かめる）

| 項目 | 値 |
|---|---|
| 実行環境を示す環境変数 | 開発／テスト用の値（本番を指さない） |
| 外部サービスへの送信（投稿・通知など）のモード | dry-run（実際には送らない） |
| DB / baseURL | baseURL（Web のとき）はローカル（`127.0.0.1` か `localhost`）。DB は `CLAUDE.md`「検証コマンド」表の『テスト用 DB』行の値に従う |
| AI | モックまたはテストキー |
| 決済サービス | test / sandbox |
| メール | ローカルで捕捉する受信箱（外へ送らないテスト用のメールサーバー） |

Web 以外は、表のうちプロジェクトにある項目だけ確かめる（外部サービスへの送信・課金などが無ければ「該当なし」）。

**やらない**: 本番接続、外部サービスへの実投稿・実送信、実課金、第三者への実メール。秘密値をスクショ・trace・ログ・報告に残さない（保存先は `/docdd:playwright-cli` の「保存先」）。

## 落とし穴（原則だけ。症状と対策は `references/pitfalls.md`）

- **「済んだ状態」をデータで直接作ったら、飛ばした入口を別ケースで1回通す。** 連携・登録・課金など。外部サービスへは行かず、リダイレクト先や発行された cookie の確認で止めてよい。
- **表示するものは実データで描画し、読み込めたところまで見る。** 要素の存在では足りない（画像なら `naturalWidth>0`）。
- **ジョブはローカルで自動では進まない。** 実行口を明示的に叩き、完了は期限付きで待つ。
- **終了コードだけで合格にしない。** テストが 0 件でも成功で終わる道具がある（例: Unity）。実行件数と失敗数を見る。
- **1件目の timeout を「flaky」（ときどき落ちる不安定なテスト）と即断しない。** 編集を挟まず再実行して見る。
- **flaky を無条件の再試行で隠さない。** 原因と再現条件を先に探す（`docs/operations/development-and-testing.md` §5）。
- **外部サービスへの依存を、テストのたびに通さない。** 相手のスクリプト配信だけ差し替え、サーバー側の検証は本物のまま通す。本物を通すのは1件だけ。
- **通り過ぎる途中の状態を検査しない。** 速さで結果が変わる検査にしない。
- **状態を作る前に、画面側で動いている繰り返し処理を捨てる**（reload してから作る）。

## 変更別に見る経路（該当のみ）

| 変更 | 通す経路 |
|---|---|
| 認証 | 登録 → 確認メール → ログイン → ログアウト → パスワード再設定 → ログイン必須の画面 |
| フォーム | 正常／入力検証／二重送信／読み込み中／再試行 |
| 外向きの送信（外部サービスへの投稿・通知など） | 作成（AI 生成があればそれも）→ ジョブ完了 → 送る内容の編集 → dry-run 送信 → 送信結果の記録 |
| 予約実行・定時処理 | 予約の登録 → 予定時刻の到来処理（dry-run）→ 同じ回の再実行で重複しないこと |
| 課金 | test 環境で契約状態と画面の権限 |
| UI（Web） | 狭い幅／キーボード／label／focus |
| ゲームのシーン・操作（Web 以外） | シーンを読み込む → 主要な操作 → 期待する状態（出るはずのオブジェクト・値・次のシーン）。自動テストで見られない見た目は「運営者確認待ち」 |

## ルール

- live 外部サービス（本物の外部サービス）が必要になったら停止し、`tasks/BACKLOG.md` の「要決定」へ書いて運営者の判断を仰ぐ（勝手に本物へ接続しない）。
- 認証・課金・同意・外向き送信の安全策（dry-run 等）を迂回しない。
- ブラウザで開くのはローカルだけ。E2E のために公開先（本番）を開かない。
- 「E2E合格」は自動シナリオが全 assertion（期待値の確認）を通過したときだけ。実行件数が 0 なら合格と呼ばない。探索的確認は「確認済み（自動回帰は保証しない）」と書く。

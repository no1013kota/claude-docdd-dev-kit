# verify-e2e の落とし穴（症状 → 見る場所 → 対策）

`SKILL.md` の「落とし穴」の詳しい版。当てはまる症状が出たときだけ読む。このプロジェクトに無い機能（外部連携・ジョブ・bot 対策など）の行は飛ばす。

| 症状 | 見る場所 | 対策 |
|---|---|---|
| E2E は緑なのに、連携・登録・課金の入口だけが実際には動かない | 前提データを直接 insert して「連携済み」「登録済み」を作っているテスト | 飛ばした入口を別ケースで1回通す。外部サービスには行かず、リダイレクト先（`Location`）や発行された cookie の確認で止めてよい |
| 画像・グラフ・外部から取得したカードがローカルで表示されないのに、E2E は緑 | 要素の存在だけを見ている assertion／CSP（読み込み許可の設定）の `img-src`／署名 URL の期限／ブラウザのコンソール | 表示するものを持つデータで実際に描画し、読み込めたこと（画像なら `naturalWidth>0`）を確かめる。CSP 違反・署名 URL の失効・デコード失敗は、実物を描画したときにしか出ない |
| ジョブの結果を待つテストが終わらない、または時間切れになる | ジョブの実行口（worker のエンドポイントや定時処理）が呼ばれているか | 実行口を明示的に叩き、完了は期限付きで poll（一定間隔で確認）する。無制限に待たない |
| コードを編集した直後の1件目だけ timeout になる | 開発サーバーの初回コンパイル | 編集を挟まず再実行する。緑なら初回コンパイルの遅さ。編集していないのに落ちたなら本物の失敗として扱う |
| 単独で回すと緑なのに、通しで回すと落ちる。繰り返すほど失敗が増え、待ち時間を伸ばしても直らない | ログインなどで毎回通っている外部サービス（例: bot 対策の人間確認ウィジェット）への要求の数 | 依存そのものを断つ。ウィジェットのスクリプトの配信だけをスタブ（偽物）へ差し替え（例: Playwright なら `page.route`）、サーバー側の検証は本物のまま通す（bot 対策サービスが用意する「常に成功するテスト用の secret」をローカルのサーバー側に設定する）。本物のウィジェットは1件だけ残し、許可ドメインなど相手側の設定は変更影響表（`.claude/rules/docdd-kit.md`「変更影響 → 必須の検証」）の「外部サービス側の設定に依存する画面」の行で見る |
| 「登録直後は `pending`」のような検査がときどき落ちる | 登録直後に走る後続ジョブ（外部 API のキーがダミーだと即失敗して状態が先へ進む） | 見たいのが「登録された」なら、行の存在で見る。速さで結果が変わる検査にしない |
| 状態を整えたはずなのに、直後に新しいジョブが増えている | 画面の「終わるのを待って次を起票する」繰り返し処理 | 画面を reload して繰り返し処理を捨ててから、状態を作る |

## キット共通の約束（docdd）

### 前提：運営者は個人（非エンジニア想定）

このシステムは **1人の運営者が非エンジニアとして運用する**。**修正の量よりも運営のしやすさを優先する**。
実装の選択で迷ったら、次を満たす方を選ぶ。「動くが運営者には扱えない」形で完了扱いにしない。

1. **黙って壊れない** — 失敗は必ず記録する。**正常な空と失敗による空を別の値で表す**（例: 検索結果0件が「該当なし」なのか「取得失敗」なのかを呼び出し側が説明できる）。運営者が気付ける経路（通知・状態確認コマンド）へ載せる。
2. **原因が開発知識なしで辿れる** — 画面かコマンド1つで「いま何が起きているか」が分かる。ログを読ませない。
3. **手順を人間の記憶に依存させない** — 欠かせない手順（DB変更の適用など）は1コマンドへ畳むか、忘れたら止まる形にする。
4. **費用が見える** — 従量課金（AI・外部API）の実績と上限超過を運営者が把握できる。
5. **判断はまとめて求める** — 小さな確認を何度も挟まず、決めるべきことを整理して提示する（判断は「要決定」へ集約）。

この原則に反する実装を見つけたら、指摘して直す。回避策をドキュメントに書いて済ませない（手動の回避策は忘れられる）。

### 最重要ルール：ドキュメントとコードの同期

`docs/` 配下は常に実装の現状と一致していなければならない（Single Source of Truth＝正本は1か所）。運営者が先に書き換えた仕様は、実装に合わせて戻さない（何も書かずに `/docdd:add-task` を打ってタスクにし、実装を追いつかせる）。

1. 仕様に影響する変更（機能追加・挙動変更・DB変更・API変更・画面変更・プロンプト変更）を実装したら、**同じ作業単位の中で**該当ドキュメントを更新する。ドキュメント更新までがタスクの完了条件。
2. どのドキュメントを更新すべきかは `docs/README.md` の地図と所有ルールに従う。
3. 要件そのものが変わる場合は PRD を更新し、変更履歴に追記する。実装詳細は PRD ではなく `docs/requirements/` の担当文書に書く。
4. コミット前に `/docdd:doc-sync` で同期漏れを見つける。`/docdd:dev-loop`・`/docdd:refactor`・`/docdd:speed-up`・`/docdd:security-audit`・`/docdd:ui-polish` は中で呼ぶので要らないが、**スキルを通さずにコードを直したときは必ず自分で実行する**（仕様書と実装がずれたままコミットしない）。
5. ドキュメントに書かれていない仕様判断を実装したら必ず正本へ書き戻す。技術判断は `docs/decisions/` に ADR として記録する。

### 開発の進め方

- スキルの呼び方: Claude Code は `/docdd:dev-loop`、Codex は `$docdd:dev-loop`（この文書とスキルの中では `/docdd:` と書く。Codex で打つときは `$` に読み替える）。
- 流れ: 要望 → `/docdd:add-task`（運営者が仕様書を書いた・書き換えたあとは、何も書かずに打つと仕様書からまとめて起票）→ `/docdd:dev-loop`（中で `/docdd:doc-sync` と検証スキルを呼ぶ）→ 依頼が全部終わったら `/docdd:release`。連続自動開発は `/loop /docdd:dev-loop`。
- 本番へ出す前に、必要なら仕上げを回す: `/docdd:refactor`（振る舞いを変えずに中身を整える）・`/docdd:speed-up`（表示が遅い）・`/docdd:security-audit`（公開前や、ログイン・課金・外部連携を触ったあと）。どれも `/docdd:release` の前に終わらせる。
- タスクは `tasks/BACKLOG.md` で管理する。状態と書式は同ファイルの「運用ルール」に従う。**終わったタスク（`done`・`dropped`）と決まった判断は `node scripts/backlog-archive.mjs` で `tasks/archive/BACKLOG-done.md` へ移す**（BACKLOG を短く保ち、未着手のタスクを見つけやすくする）。アーカイブは丸ごと読まず、ID や言葉で検索する。新しい T-番号・D-番号は、アーカイブも含めた最大の次にする。
- **要望を受け取ったら `/docdd:add-task <要望>` で起票してから実装へ進む。** `todo` が1件も無ければ、`/docdd:dev-loop` は起票のしかたを伝えて止まる。
- 1タスク = 1コミット。コミットメッセージにタスクIDを含める（例: `feat(T-01): メール認証を実装`）。
- コミットに運営者の承知が要るプロジェクト、決まったブランチ運用があるプロジェクトは、`AGENTS.md`「スキルへの追加指示」に書く（スキルは本文より追加指示を優先する）。
- ユーザー判断が必要な事項は勝手に決めず、`tasks/BACKLOG.md` の「要決定」へ追記して先へ進む（可能なら暫定案を添える）。決まったら正本（事業判断は `docs/PRD.md`、画面・データの細部は `docs/requirements/`、技術判断は `docs/decisions/` の ADR）へ書き戻す。
- 仕様の読み方: 何を作るか → `docs/PRD.md`。どう作るか（画面・DB・処理）→ `docs/requirements/`。ほかに運営者が `docs/` に置いた仕様書も、仕様の正本として扱う（`docs/_imported/` の原文は除く）。version はファイル名ではなく文書冒頭の表を正とする。
- 検証と反映のコマンドは `AGENTS.md` の「検証コマンド」「反映コマンド」表のものを使う。値が「無い」の行は飛ばし、二重波かっこ（`{{…}}`）のままの行は未記入として実行しない。どちらも理由を報告する（黙って省略しない）。

### 変更影響 → 必須の検証

外部サービス・ブラウザ・メールなど、**境界をモックしたテストでは確かめられない**所があるため、触った層で必須の検証を対応表で機械的に決める（判断で選ばない）。**該当行が複数あればすべて実行する**。実行しなかった行がある場合は理由を報告する（黙って省略しない）。このプロジェクトに無い層（課金・定時処理・外部 AI など）の行は「該当なし」と報告する。

**触った層は、未コミットの変更と直近のコミットの両方から特定する** — `git status --short` と `git diff HEAD` に加えて、`git log --oneline -10` で今回の作業に当たるコミットの範囲を見て `git diff <その手前のコミット>..HEAD` を読む（コミットがまだ 1 つも無ければ未コミット分だけでよい）。コミットしたあとや、別の会話で「テストして」と頼まれたときも、直近のコミットまで見る。どこまでが今回の変更か決まらないときは、推測せず運営者に聞く。

表の『』で囲んだ名前は、`AGENTS.md`「検証コマンド」表の行を指す。

| 触った層 | 必須の検証 |
|---|---|
| DB のスキーマ・権限・migration | `/docdd:verify-integration`（ロール権限を含む） |
| サーバー側の処理（API・Server Action） | 本番実装を実 DB（『テスト用 DB』）で通すテスト |
| **DB へ書く値の形式**（キー・列挙・日付書式） | その値を**実際に insert する**テスト（文字列の組み立てを見る単体テストでは足りない） |
| **外部 AI／外部 API の呼び出し・プロンプト・出力の形** | 受理されるかの検査 ＋ **実物で1周**（実 API で成果物まで見る） |
| **画面（Web）** | `/docdd:ui-polish` ＋ **実データを描画する E2E**（画像・表・レイアウト崩れはブラウザでしか出ない） |
| **画面・操作（Web 以外）**（ゲームのシーン・UI、ネイティブアプリの画面） | 『E2E（実際に動かす）』行の自動テスト（例: Unity の PlayMode テスト）。自動テストで確かめられない見た目・操作は、運営者に確かめてもらう手順（開く場面・操作・期待する見え方）を示し、報告に「運営者確認待ち」と書く |
| **エンジンやツールが保存するファイル**（ゲームエンジンのシーン・プレハブ・.meta、Xcode・Android Studio のプロジェクト設定など） | 手で書き換えず、エンジンやツールの操作か、その API を使うスクリプトで変える。対になるファイル（Unity の .meta など）の増減を `git status` で確かめ、報告に載せる |
| 外向き副作用（外部サービスへの送信・メール・課金・外部サービス上のデータの削除） | 非本番で実行されないことの確認（環境ガードの有無） |
| **古いものを消す処理**（保持期間つきの削除、どこからも使われていないものの掃除） | 消される側を**指しうる場所をすべて列挙**し、**「参照あり」と「参照なし」を 1 件ずつ置いて、参照ありだけが残る**ことを本物（『テスト用 DB』・実際に置いたファイル）で確かめる（両方を置くと、消しすぎも消し忘れも見つかる）。判定が複数か所（1 件ずつ確かめる側と、一括で拾う側）にあるなら、そのすべてで確かめる |
| **本番ビルドでしか出ない設定**（CSP・キャッシュ・事前描画） | 『ビルド』＋『本番モード起動』＋ 実ブラウザで公開ページのコンソールエラーまで見る |
| **外部サービス側の設定に依存する画面**（人間確認・OAuth・決済） | 実ブラウザ。相手側の許可ドメイン等はコードに現れない |
| 定時処理 | `/docdd:verify-integration` ＋ 該当処理を実際に1回動かし、**結果の中身**まで確認 |
| **検査そのもの**（テスト・lint 規則・規約を機械で守るスクリプト）を足した・変えた | **わざと違反を入れて、その検査が落ちることを 1 度確かめて**から元へ戻す（`docs/operations/development-and-testing.md` §3（テストを書くときの決まり）・§5（落とし穴））。走査して違反を探す検査なら、**検出のしかたごとに「1 件以上当たること」**も検査に入れる（検出のしかたごとに見ると、1 つだけ空振りしていても分かる） |
| **ドキュメントのみ（docs・tasks・AGENTS.md）** | `/docdd:doc-sync` ＋『docs の検査』＋『未記入欄の検査』（参照先ファイルの実在と、埋め忘れの欄を確かめる） |
| 上記以外 | 『全検査（push 前に1回）』 |

**公開先へ反映したとき**は、公開先の画面を実際に開いて確認したことまで報告に含める（公開先の設定値は、手元のテストでは確かめられない）。

**migration（DB の構造変更）を含む反映**では、本番 DB を変える前に `/docdd:release` がバックアップを取る（`AGENTS.md`「反映コマンド」表の『本番 DB のバックアップ』行に従う）。取れなければ反映しない。行が未記入なら、その場で候補を示して聞き、決めた内容を行へ書く。

**公開した版に不具合が出たとき**に前の版へ戻す手順は、`AGENTS.md`「反映コマンド」表の『戻し方』行に書く。バックアップは**データ**を戻すため、『戻し方』は**版**を戻すためのもので、別物（版を戻しても DB はそのまま）。戻し方と、控えに入らないもの（利用者が上げたファイル・外部サービス側の設定）は `docs/operations/backup-and-restore.md`。

**「実物を1周」の意味**: リクエストが受理されることでは足りない。**応答をアプリが扱えて、最終成果物が正しいところまで**見る。費用が出るので、`AGENTS.md`「検証コマンド」表の『実物1周の費用上限』行の金額を上限にし、超えたら止めて報告する。**その行が未記入（または「無い」）なら、実物1周は実行せずに報告する。**

いつ回すか（変更ごと・コミット前・push 前）と、踏みやすい落とし穴は `docs/operations/development-and-testing.md` の §2（いつ回すか）と §5（落とし穴）を見る。

### Definition of Done（全タスク共通）

- [ ] 実装が完了し、テストが通る（テスト基盤がまだ無いときは、未検証であることと「テスト基盤の導入」タスクの ID を報告した）
- [ ] **「変更影響 → 必須の検証」の該当行をすべて実行した**（未実行の行は理由を報告した）
- [ ] UI 変更では、Web なら `/docdd:ui-polish` の画面幅・主要状態・アクセシビリティ・実ブラウザ検証が、Web 以外なら変更影響表の「画面・操作（Web 以外）」行の確認が完了している
- [ ] `/docdd:doc-sync` 実行済み（該当ドキュメントを更新した、または影響なしを理由付きで確認した）
- [ ] `tasks/BACKLOG.md` のステータスを更新し、「実装メモ:」「検証:」の 2 行を足してから、`node scripts/backlog-archive.mjs` で終わったものをアーカイブへ移した
- [ ] タスクIDを含むメッセージでコミットした

### 規約

- ドキュメント・コミットメッセージ・ユーザーへの応答は日本語。ただしプロジェクトの既存の文書・コミットが別の言語なら、それに合わせる（決め方は `AGENTS.md`「スキルへの追加指示」に書いてよい）。コードの識別子・コード内コメントは英語。
- **`git add -A`（や `git add .`）を使わず、パスを明示して `git add` する。** 利用者が並行して編集中のファイルを巻き込むため（プラグインの hook も止める）。
- 秘密情報（APIキー・トークン・暗号鍵）は `.env` だけに置く（`/docdd:init` が .gitignore で除外されているかを確認する）。変数名の一覧は値を書かずに `.env.example` へ書く。コード・ドキュメント・コミットに実キーを書かない。
- スクショ・trace・計測用の一時ファイルはコミットしない。置き場は `/tmp/claude/`（Web のプロジェクトでは、playwright-cli が自動で作る `.playwright-cli/` も .gitignore 済み）。
- 外部 API の仕様は変更が頻繁。該当箇所の実装時は必ず公式ドキュメントで最新仕様を確認する。

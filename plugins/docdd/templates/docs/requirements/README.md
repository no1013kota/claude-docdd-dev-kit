# 要件詳細の分け方

PRD の「何を作るか」を「どう作るか」に落とした文書をここに置く。1文書1担当範囲。

**最初は 06_screens.md（画面ごとに何が見えて何ができるか）の1本だけで十分。** 必要になったら下の表から増やす。全部を最初にそろえない。

## 1. 文書の分け方

| 文書名（例） | 担当範囲 | 見出し ID の接頭辞 |
|---|---|---|
| 01_system_architecture.md | 技術スタック、環境変数、認証、監視 | 無し（ID を付けなくてよい） |
| 02_data_model.md | テーブルの列・制約・保持期間 | D |
| 03_auth_billing.md | 登録・ログイン、課金、利用枠 | P |
| 04_jobs.md | 定時処理、ジョブ、通知 | P |
| 05_api.md | API・サーバー処理の入出力、エラー、認可 | API |
| 06_screens.md | 画面ごとの仕様、文言の方針 | S |

使わない領域（課金・ジョブなど）の文書は作らない。

## 2. 見出し ID の規則

- 画面・テーブル・処理・API の1つごとに、ID 付きの見出しを立てる。書き方の例: `## S-01 予約一覧`
- 接頭辞は S=画面、D=データ、P=処理、API=API。番号は文書ごとの連番（01, 02…）。消した番号は使い回さない。
- 接頭辞は文書ごとに足してよい（例: ゲームのルールは RULE-01）。足したら上の表の「見出し ID の接頭辞」の列にも書く。
- タスクからはファイル名と ID で指す。書き方の例: `PRD A-1 / requirements/06_screens.md S-01`。requirements がまだ無ければ `PRD A-1（requirements は本タスクで追記）` と書く（`tasks/BACKLOG.md` の運用ルール）。

## 3. 書き方

- 新しい文書は雛形 `00_template.md` をコピーして、上の表の名前にする。
- 冒頭に「バージョン」（v0.1 から始める）と「更新日」の2行の表、末尾に変更履歴の表を持つ（雛形のとおり）。version は v を付けて書く。v を省くと docs の検査が変更履歴を読めない。
- まだ実装が無い部分は「未実装」と書く。実測した数値は「実測が正」と明記し、測った日付を添える。
- 料金・スコープなどの事業判断は書かない。PRD か `tasks/BACKLOG.md` の「要決定」へ。

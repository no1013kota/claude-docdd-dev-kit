# ドキュメントマップ

`docs/` は仕様の正本（Single Source of Truth＝同じことを書く場所は1か所）。**実装と食い違った状態を放置しない。**

## 1. どこに何があるか

| ファイル・フォルダ | 何が書いてあるか | 主な節 | 更新するとき |
|---|---|---|---|
| `docs/PRD.md` | PRD。何を作るか・なぜ。スコープ、料金、上限 | 機能一覧＝§3.1、やらないこと＝§3.2、主な画面（ゲームならシーン）と利用者の流れ＝§3.3、料金・上限＝§4、変更履歴＝§6 | 要件・料金・スコープ・上限が変わる |
| `docs/requirements/` | 要件詳細。どう作るか（画面・データ・処理・API） | 各文書の見出し ID の節（S=画面、D=データ、P=処理、API=API）。分け方と ID の規則は [README.md](./requirements/README.md)、雛形は [00_template.md](./requirements/00_template.md) | 実装の構造が変わる |
| `docs/` に自分で置いた仕様書（ある場合） | PRD・要件詳細のほかに置いた仕様 | 見出しの付いた節 | 仕様が変わる |
| `docs/operations/development-and-testing.md` | 開発とテストの進め方。テストの層と盲点、検証を回すタイミング | テストの層＝§1、いつ回すか＝§2、テストを書くときの決まり＝§3、テスト基盤が無いとき＝§4、落とし穴＝§5 | 検証手段が変わる |
| `docs/operations/backup-and-restore.md` | 控えと戻し方。控えに何が入り・何が入らないか、戻す手順、戻せたことを確かめた記録 | 何を守るか＝§1、置き場所＝§2、データを戻す＝§3、公開した版を戻す＝§4、確かめた記録＝§5 | 控えの取り方・置き場所・戻し方が変わる／復元を試した |
| `docs/decisions/` | ADR。上記で表現しきれない技術判断の記録 | 1判断1ファイル。一覧は [README.md](./decisions/README.md) の「ADR 一覧」、雛形は [0000-template.md](./decisions/0000-template.md) | 後から変えにくい選択をしたとき（決めたことが変わったら本文を書き換えず「改訂」行を足す） |
| `CLAUDE.md` | このプロジェクトだけのこと（構成・コマンド・スキルへの追加指示） | 「検証コマンド」「反映コマンド」「スキルへの追加指示」の表 | コマンド・ブランチ・公開先が変わる／このプロジェクトだけの指示を足す |
| `.claude/rules/docdd-kit.md` | どのプロジェクトでも同じ約束（5原則・変更影響 → 必須の検証・Definition of Done・規約） | 「変更影響 → 必須の検証」の表 | 直さない（`/docdd:update-kit` が新しい版にする。このプロジェクトだけの指示は `CLAUDE.md` の「スキルへの追加指示」へ） |
| `docs/_imported/`（ある場合） | 導入前からあった仕様書・メモの原文 | 冒頭1行に正本の場所 | 直さない（下の「取り込んだ原文」） |

何も書かずに `/docdd:add-task` と打ったときにタスクの元にするのは、PRD・要件詳細の各文書・自分で置いた仕様書。この README・`docs/requirements/` の README と雛形・`docs/operations/`・`docs/decisions/`・`docs/_imported/` はタスクの元にしない。

PRD や要件を自前の書式で持ち込んだら、「主な節」の列を実際の節の名前に書き換える。スキルはこの表を読んで節を探す。

**取り込んだ原文**: 導入前からある仕様書（README・Notion の書き出しなど）は `docs/_imported/` へ原文のまま移し（`git mv` を使う）、冒頭に1行「正本は docs/PRD.md（YYYY-MM-DD 移行）」と書く。中身は PRD（必要なら requirements）へ移し、以後は原文を直さない。

## 2. 仕様の所有ルール（どこに書くか）

| 書くこと | 正本 | 他の文書には |
|---|---|---|
| 機能の有無、プラン差、料金、上限 | PRD | 参照だけ |
| DB・API・画面・処理の数値と構造 | `requirements/` の担当文書 | 要約だけ |
| 検証・反映のコマンド、公開先 | `CLAUDE.md` の表 | 参照だけ |
| 未決の事業判断 | `tasks/BACKLOG.md`「要決定」 | 重複記載しない。決まったら正本へ書き戻す（書き戻し先と「状態」行の書き方は [decisions/README.md](./decisions/README.md) の「要決定からの書き戻し」） |

**同じ数字を2か所に置かない。** 1つの変更が複数文書へ影響するなら同じ作業単位で更新する。

## 3. コードとのズレを止める仕組み

一覧や数値は、手で数え上げるのではなく、**機械が突き合わせる**検査で守る（例: docs 内のファイルパスが実在するか、docs の更新日がその文書を最後に変えたコミットの日付と合っているか、docs の表と DB の列が一致するか）。**新しく一覧や数値を docs へ書くときは、突き合わせる検査も同時に作る。** 作れないなら「実測が正」と明記して日付を添える。

このキットに最初から入っている検査は4本。実行するときは `CLAUDE.md`「検証コマンド」表の行を使う。

| ファイル | 表の行 | 見るもの |
|---|---|---|
| `scripts/check-doc-refs.mjs` | docs の検査 | docs が指すファイルの実在（対象は下の「参照の検査の対象」）と、`docs/decisions/` の ADR がすべて `decisions/README.md` の「ADR 一覧」に載っているか |
| `scripts/check-doc-dates.mjs` | docs の検査 | 更新日が、その文書の内容を最後に変えたコミットより古くないか。冒頭の version と変更履歴が合っているか |
| `scripts/check-doc-placeholders.mjs` | 未記入欄の検査 | 二重波かっこ（`{{…}}`）の埋める欄が残っていないか。対象は `CLAUDE.md`・`.claude/rules/`・`docs/`・`tasks/` の Markdown。インラインコード・コードブロック・HTML コメントの中は数えない |
| `scripts/audit-check.mjs` | 依存の脆弱性 | 本番の依存ライブラリの high 以上の脆弱性（docs の検査ではない。npm と package-lock.json のプロジェクト用）。high を据え置くなら `scripts/audit-allowlist.json` に、パッケージ名ごとに脆弱性の ID（`ids`。GHSA- で始まる）・理由（`why`）・期限（`until`）を書く（3 つとも必須。critical は据え置けない）。npm 以外は『依存の脆弱性』行のコマンドを使い、据え置くなら `tasks/BACKLOG.md` の「要決定・外部準備」に ID・理由・期限を書く |

**参照の検査の対象**: `CLAUDE.md`・`.claude/rules/`・`docs/` の Markdown のうち、(1) バッククォートで囲んだファイルパスで、拡張子が `scripts/check-doc-refs.mjs` の EXTS にあるもの（md・js・ts・py・cs・unity・prefab・gd・dart・swift など）、(2) `[PRD](./PRD.md)` のような `](./…)`・`](../…)` の形の相対リンク。

次の所は書き方の見本として見ない（見本に出すファイル名は実在しなくてよい）。判定は行ごとで、これ以外の行は、前の行に「例」があっても検査する。

- 「例」という字を含む行（「例外」の「例」は数えない）。
- HTML コメントの中と、コードブロックの中。
- 行末が「例えば」「たとえば」「for example」「for instance」「e.g.」（コロンを付けてもよい）で終わる行の、すぐ下に続く箇条。間に空行が 1 行あってもよい。

`check-doc-*.mjs` の 3 本は、git が追跡しているファイルだけを見る（**新しく作ったファイルは先に `git add` する**）。`docs/_imported/` 配下と、雛形の `docs/requirements/00_template.md`・`docs/decisions/0000-template.md` は対象外。更新日の表を持たない文書（README・ADR など）は日付の検査の対象外。

## 4. 更新ルール

- **version は文書冒頭の表を正とする。** ファイル名に version を含めない。
- 仕様の正本（PRD と requirements の各文書）は、冒頭に「バージョン」「更新日」の2行の表、末尾に「変更履歴」の表を持つ（形は `docs/requirements/00_template.md` のとおり）。自分で置いた仕様書も同じ形にすると、『docs の検査』が更新日と変更履歴を見る。
- 検査が認識する見出し語: 冒頭の表は「バージョン」か「version」、「更新日」か「最終更新日」。変更履歴の表の見出し行は `| バージョン | 日付 | 内容 |`。version は `v0.1` のように v を付けて書く。
- 仕様変更時は冒頭の**更新日**と末尾の**変更履歴**を更新する。表記修正だけなら version は上げない。
- 変更履歴の「内容」には**きっかけ**を添える。タスクなら `T-01`、要決定なら `D-1`、運営者の判断で変わったなら「運営者の指示 YYYY-MM-DD」。書き方の例: `| v0.2 | 2026-09-10 | 前日のお知らせ（A-6）を追加（T-03） |`。半年後に「なぜこうなっているか」を辿る手がかりになる。きっかけの無い変更（表記の修正など）は省いてよい。
- 変更履歴の並びは自由（古い順でも新しい順でもよい。最新版が分かればよい）。
- 運営者が PRD・要件詳細・自分で置いた仕様書を書き換えたら、何も書かずに `/docdd:add-task` と打ち、書き換えた所をタスクにする。タスクになった書き換えはコミットしなくてよい（そのタスクの `/docdd:dev-loop` が、更新日・変更履歴と一緒にコミットする）。タスクにならない書き換え（表記の直しなど）は、`/docdd:add-task` が承知を得てコミットする。
- コードがまだない領域は「未実装」であることを明記する。

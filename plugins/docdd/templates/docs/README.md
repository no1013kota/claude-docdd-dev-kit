# ドキュメントマップ

`docs/` は仕様の正本（Single Source of Truth＝同じことを書く場所は1か所）。**実装と食い違った状態を放置しない。**

## 1. どこに何があるか

| 文書 | 何が書いてあるか | 主な節 | 更新するとき |
|---|---|---|---|
| [PRD](./PRD.md) | 何を作るか・なぜ。スコープ、料金、上限 | 機能一覧＝§3.1、やらないこと＝§3.2、主な画面と利用者の流れ＝§3.3、料金・上限＝§4、変更履歴＝§6 | 要件・料金・スコープ・上限が変わる |
| [要件詳細](./requirements/README.md) | どう作るか（画面・データ・処理・API） | 文書の分け方＝§1、見出し ID の規則（S=画面、D=データ、P=処理、API=API）＝§2。雛形は [00_template.md](./requirements/00_template.md) | 実装の構造が変わる |
| [開発とテストの進め方](./operations/development-and-testing.md) | テストの層と盲点、検証を回すタイミング | テストの層＝§1、いつ回すか＝§2、テスト基盤が無いとき＝§4、落とし穴＝§5 | 検証手段が変わる |
| [ADR](./decisions/README.md) | 上記で表現しきれない技術判断 | 1判断1ファイル。雛形は [0000-template.md](./decisions/0000-template.md) | 後から変えにくい選択をしたとき |
| [CLAUDE.md](../CLAUDE.md) | このプロジェクトのコマンドと、スキルへの追加指示 | 「検証コマンド」「反映コマンド」「スキルへの追加指示」の表 | コマンド・ブランチ・公開先が変わる |
| [キット共通の約束](../.claude/rules/docdd-kit.md) | 5原則・変更影響 → 必須の検証・Definition of Done・規約 | 「変更影響 → 必須の検証」の表 | 直さない（キットが管理する） |
| docs/_imported/（ある場合） | 導入前からあった仕様書・メモの原文 | 冒頭1行に正本の場所 | 直さない（下の「取り込んだ原文」） |

PRD や要件を自前の書式で持ち込んだら、「主な節」の列を実際の節の名前に書き換える。スキルはこの列を頼りに節を探す。

**取り込んだ原文**: 導入前からある仕様書（README・Notion の書き出しなど）は `docs/_imported/` へ原文のまま移し（`git mv` を使う）、冒頭に1行「正本は docs/PRD.md（YYYY-MM-DD 移行）」と書く。中身は PRD（必要なら requirements）へ移し、以後は原文を直さない。`docs/_imported/` 配下は docs の検査と未記入欄の検査の対象外。

## 2. 仕様の所有ルール（どこに書くか）

| 種類 | 正本 | 他の文書には |
|---|---|---|
| 機能の有無、プラン差、料金、上限 | PRD | 参照だけ |
| DB・API・画面・処理の数値と構造 | `requirements/` の担当文書 | 要約だけ |
| 検証・反映のコマンド、公開先 | `CLAUDE.md` の表 | 参照だけ |
| 未決の事業判断 | `tasks/BACKLOG.md`「要決定」 | 重複記載しない。決まったら正本（事業判断は PRD、技術判断は ADR）へ書き戻し、要決定の「状態」行を「決定（日付・選んだ案）→ 書き戻し先」に書き換える |

**同じ数字を2か所に置かない。** 片方だけ古くなる。1つの変更が複数文書へ影響するなら同じ作業単位で更新する。

## 3. コードとのズレを止める仕組み

**手で数え上げた一覧は必ず古くなる。** だから**機械が突き合わせる**検査を作る（例: docs 内のファイルパスが実在するか、docs の更新日がその文書を最後に変えたコミットの日付と合っているか、docs の表と DB の列が一致するか）。**新しく一覧や数値を docs へ書くときは、突き合わせる検査も同時に作る。** 作れないなら「実測が正」と明記して日付を添える。

このキットに最初から入っている検査は4本。実行するときは `CLAUDE.md`「検証コマンド」表の行を使う。

| 検査 | 表の行 | 見るもの |
|---|---|---|
| `scripts/check-doc-refs.mjs` | docs の検査 | docs が指すファイルの実在（対象は下の「参照の検査の対象」） |
| `scripts/check-doc-dates.mjs` | docs の検査 | 更新日が、その文書の内容を最後に変えたコミットより古くないか。冒頭の version と変更履歴が合っているか |
| `scripts/check-doc-placeholders.mjs` | 未記入欄の検査 | 二重波かっこ（`{{…}}`）の埋める欄が残っていないか。対象は `CLAUDE.md`・`.claude/rules/`・`docs/`・`tasks/` の Markdown。インラインコード・コードブロック・HTML コメントの中は数えない |
| `scripts/audit-check.mjs` | 依存の脆弱性 | 依存ライブラリの high 以上の脆弱性（docs の検査ではない）。据え置くものは `scripts/audit-allowlist.json` に理由を添えて書く |

**参照の検査の対象**: `CLAUDE.md`・`.claude/rules/`・`docs/` の Markdown のうち、(1) バッククォートで囲んだファイルパスで、拡張子が md・js・jsx・ts・tsx・mjs・cjs・py・go・rb・php・sql・toml・json・yml・yaml・css・sh・prisma のもの、(2) `[PRD](./PRD.md)` のような `](./…)` の形の相対リンク。「例」という字を含む行と HTML コメントの中は見ない（例に出すファイル名は実在しなくてよい）。

どの検査も git が追跡しているファイルだけを見る（**新しく作ったファイルは先に `git add` する**）。`docs/_imported/` 配下と、雛形の `docs/requirements/00_template.md`・`docs/decisions/0000-template.md` は対象外。更新日の表を持たない文書（README・ADR）は日付の検査の対象外。

## 4. 更新ルール

- **version は文書冒頭の表を正とする。** ファイル名に version を含めない。
- 仕様の正本（PRD と requirements の各文書）は、冒頭に「バージョン」「更新日」の2行の表、末尾に「変更履歴」の表を持つ（形は `docs/requirements/00_template.md` のとおり）。
- 検査が認識する見出し語: 冒頭の表は「バージョン」か「version」、「更新日」か「最終更新日」。変更履歴の表の見出し行は `| バージョン | 日付 | 内容 |`。version は `v0.1` のように v を付けて書く。
- 仕様変更時は冒頭の**更新日**と末尾の**変更履歴**を更新する。表記修正だけなら version は上げない。
- 変更履歴の並びは自由（古い順でも新しい順でもよい。最新版が分かればよい）。
- コードがまだない領域は「未実装」であることを明記する。
- コミット前に `/docdd:doc-sync` を実行する。

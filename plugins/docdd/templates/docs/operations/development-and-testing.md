コマンドはすべて `AGENTS.md`「検証コマンド」表にある（この文書にはコマンドを書かない）。

## 1. テストの層と、それぞれ見えないもの

層ごとに見えないものがあるので、1 つの層だけでは足りない。どの層を回すかは人が選ばず、`AGENTS.md` の「変更影響 → 必須の検証」の**対応表で決める**。

| 層 | 守るもの | 見えないもの |
|---|---|---|
| 1. 型・lint | 型の整合 | 実行時の振る舞い |
| 2. 単体テスト | 純粋関数・モック注入での分岐と境界値 | **モックした境界の向こう側すべて** |
| 3. DB 統合テスト | 実 DB での制約・権限・サーバー処理の本番実装。ホスト型の開発専用・破棄可能な DB で代替してよい（本番と分離していることが条件） | 外部 API・ブラウザ描画 |
| 4. E2E（実際に動かす） | 操作・遷移・実データの描画 | 外部 AI の中身、本番ビルドでしか出ない設定 |
| 5. 外部 API の受理確認 | 送っているリクエストが実 API に受理されるか | 応答をアプリが扱えるか |
| 6. 実物スモーク | 応答をアプリが扱えて成果物が正しいか | 本番固有の環境差 |
| 7. CI | 1〜4 の実行そのものを強制 | 5・6（実キーが必要） |
| 8. 外部サービス側の設定 | 相手側の設定（許可ドメイン・メール送信元）がその環境で通るか | — |

層5と層6は別物: **受理される**（5）だけでは足りず、**扱える**（6）まで見る。

## 2. いつ回すか

| いつ | 何を回すか（`AGENTS.md`「検証コマンド」表の行） |
|---|---|
| 変更ごと | 型検査 ＋ lint ＋ 単体・DBテスト |
| コミット前 | ＋ docs の検査 ＋ 未記入欄の検査（**新しく作ったファイルは先に `git add`**） |
| **push 前（まとめて1回）** | ＋ ビルド ＋ E2E（または『全検査（push 前に1回）』を1回） |

遅いのはビルドと E2E だけなので、その2つだけ push 前へまとめる。ただし「その変更に固有の検証」（外部 API の実物1周、本番ビルドでしか出ない設定、定時処理の実行）は push 前を待たずにその場で回す。

## 3. テストを書くときの決まり

- 実装詳細ではなく**公開される入出力・状態遷移・エラー**を検証する。
- 不具合修正は**修正前に失敗する再現テストを先に**書く。
- 「正常な空」と「失敗による空」を別の値で表し、テストでも区別する。
- DB を使うテストは本番と別の DB に向ける（`AGENTS.md`「検証コマンド」表の『テスト用 DB』行）。
- **検査は、落ちるところを 1 度見てから使う。** 規約を機械で守る検査や、新しく足した層の 1 件目は、最初から緑のまま書けるので、**わざと違反や不具合を入れて、その検査が落ちることを 1 度確かめる**（確かめたら §5 のとおり必ず元へ戻す）。不具合修正の再現テストは、修正前に赤を見ているのでこれを満たしている。

## 4. テスト基盤が無いとき

`AGENTS.md`「検証コマンド」表の『単体・DBテスト』（または『E2E（実際に動かす）』）が「無い」か未記入なら、テスト基盤（テストを動かす道具と設定）が無い。テストを書く前に、土台を1つのタスクで入れる（`/docdd:init` が起票する「テスト基盤の導入」。無ければ `/docdd:add-task テスト基盤の導入` で起票する）。

- 選び方の目安: TypeScript／JavaScript は vitest（単体）と @playwright/test（E2E）。Python は pytest。依存を増やしたくなければ Node.js 標準の node:test。Unity は Unity Test Framework（EditMode／PlayMode）。Godot はアドオン（addons/ に入れる追加の部品）の GUT か gdUnit4 を入れる。GDScript だけなら GUT、C# でも書くなら gdUnit4（どちらもコマンドで回せる）。ほかの言語は、その言語の標準のテスト道具（例: go test、dotnet test）。どれにするかは運営者の承知を得てから入れる。
- 最小構成: 設定ファイル1つ ＋ 見本テスト1件 ＋ 実行コマンド（Node.js なら package.json の scripts に test と test:e2e。Unity なら設定はテスト用の asmdef）。見本テスト1件が緑になったら完了。
- 選んだコマンドは `AGENTS.md`「検証コマンド」表の『単体・DBテスト』『E2E（実際に動かす）』『全検査（push 前に1回）』行に書く。ほかの文書には書かない。
- DB を使うテストは本番と別の DB に向ける。接続先は『テスト用 DB』行に書く（書き方の見本は `AGENTS.md`「検証コマンド」表の下）。
- Web の E2E は初回にブラウザ本体のダウンロード（数百 MB）が要る。依存を足す確認（npm install など）が出たら内容を読んで許可し、「常に許可」は選ばない。
- Unity: コマンドでテストを回す（batchmode）ときは、Editor で同じプロジェクトを閉じておく（開いたままなら、運営者に Editor の Test Runner で回してもらう）。終了コードに加えて、結果ファイル（XML）のテストの件数が 0 でないことも見る（0 件でも終了コードは 0）。
- Unity の PlayMode テストとビルドのコマンドは、`AGENTS.md`「検証コマンド」表の下に書き方の見本がある。

## 5. 落とし穴

- **パイプで終了コードを捨てない。** `<コマンド> | tail` の終了コードは `tail` のもの。出力はファイルへ落とし、`echo $?` を別に確認する。
- **UI・文言を触ったら、push 前に必ず E2E を回す。** 画面の文言を確かめるのは E2E だけ（単体テストは文言の変更では落ちない）。
- **docs を編集したら、同じ編集の中で冒頭の「更新日」も今日にする。** `scripts/check-doc-dates.mjs` が比べるのは「その文書の内容を最後に変えたコミットの日付」なので、コミット前に検査が通っていても更新日は直しておく。
- **E2E の 1 件目の時間切れを「flaky（たまに落ちるだけ）」と決めない。** 編集直後の初回はコンパイルに時間がかかるので、編集を挟まずにもう 1 度回して緑かを見る。編集していないのに落ちたなら、本物の失敗として扱う。
- **「何回かに 1 回落ちる」ときは、落ちた回数ではなく落ちる条件を探す**（溜まったデータの量など）。
- **失敗を注入して確かめたら、必ず元へ戻す。** 注入した行・一時ファイルの削除まで含めて1つの作業とする。

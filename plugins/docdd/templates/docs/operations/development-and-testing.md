各層・各段のコマンドは `CLAUDE.md`「検証コマンド」表にある（この文書にはコマンドを書かない）。

## 1. テストの層と、それぞれ見えないもの

**どの層も単独では不十分**で、層ごとに「原理的に見えないもの」がある。だから `.claude/rules/docdd-kit.md` の「変更影響 → 必須の検証」で、層を人が選ばず**対応表で決める**。

| # | 層 | 守るもの | **見えないもの** |
|---|---|---|---|
| 1 | 型・lint | 型の整合 | 実行時の振る舞い |
| 2 | 単体テスト | 純粋関数・モック注入での分岐と境界値 | **モックした境界の向こう側すべて** |
| 3 | DB 統合テスト | 実 DB での制約・権限・サーバー処理の本番実装。ホスト型の開発専用・破棄可能な DB で代替してよい（本番と分離していることが条件） | 外部 API・ブラウザ描画 |
| 4 | E2E（実際に動かす） | 操作・遷移・実データの描画 | 外部 AI の中身、本番ビルドでしか出ない設定 |
| 5 | 外部 API の受理確認 | 送っているリクエストが実 API に受理されるか | 応答をアプリが扱えるか |
| 6 | 実物スモーク | 応答をアプリが扱えて成果物が正しいか | 本番固有の環境差 |
| 7 | CI | 1〜4 の実行そのものを強制 | 5・6（実キーが必要） |
| 8 | 外部サービス側の設定 | 相手側の設定（許可ドメイン・メール送信元）がその環境で通るか | — |

層5と層6は別物: **受理される**（5）だけでは足りず、**扱える**（6）まで見る。

## 2. いつ回すか

| 段 | 何を回すか（`CLAUDE.md`「検証コマンド」表の行） |
|---|---|
| 変更ごと | 型検査 ＋ lint ＋ 単体・DBテスト |
| コミット前 | ＋ docs の検査 ＋ 未記入欄の検査（**新しく作ったファイルは先に `git add`**） |
| **push 前（まとめて1回）** | ＋ ビルド ＋ E2E（または『全検査（push 前に1回）』を1回） |

遅いのはビルドと E2E だけなので、その2つだけ push 前へまとめる。ただし「その変更に固有の検証」（外部 API の実物1周、本番ビルドでしか出ない設定、定時処理の実行）は段を待たずにその場で回す。

## 3. テストを書くときの決まり

- 実装詳細ではなく**公開される入出力・状態遷移・エラー**を検証する。
- 不具合修正は**修正前に失敗する再現テストを先に**書く。
- 「正常な空」と「失敗による空」を別の値で表し、テストでも区別する。
- DB を使うテストは本番と別の DB に向ける（`CLAUDE.md`「検証コマンド」表の『テスト用 DB』行）。

## 4. テスト基盤が無いとき

`CLAUDE.md`「検証コマンド」表の『単体・DBテスト』（または『E2E（実際に動かす）』）が「無い」か未記入なら、テスト基盤（テストを動かす道具と設定）が無い。テストを書く前に、土台を1つのタスクで入れる（`/docdd:init` が起票する「テスト基盤の導入」。無ければ `/docdd:add-task` で起票する）。

- 選び方の目安: TypeScript／JavaScript は vitest（単体）と @playwright/test（E2E）。Python は pytest。依存を増やしたくなければ Node.js 標準の node:test。Unity は Unity Test Framework（EditMode／PlayMode）。Godot などほかのエンジン・言語は、その標準のテスト道具（例: go test、dotnet test）。どれにするかは運営者の承知を得てから入れる。
- 最小構成: 設定ファイル1つ ＋ 見本テスト1件 ＋ 実行コマンド（Node.js なら package.json の scripts に test と test:e2e。Unity なら設定はテスト用の asmdef）。見本テスト1件が緑になったら完了。
- 選んだコマンドは `CLAUDE.md`「検証コマンド」表の『単体・DBテスト』『E2E（実際に動かす）』『全検査（push 前に1回）』行に書く。ほかの文書には書かない。
- DB を使うテストは本番と別の DB に向ける。接続先は『テスト用 DB』行に書く（ホスト型なら「② ホスト型の開発専用: 接続先は .env の `<キー名>`（本番と別・開発専用・破棄可能）」の形）。
- Web の E2E は初回にブラウザ本体のダウンロード（数百 MB）が要る。依存を足す確認（npm install など）が出たら内容を読んで許可し、「常に許可」は選ばない。
- Unity の注意: Editor で同じプロジェクトを開いていると、コマンドでのテスト実行（batchmode）は動かない（閉じてから回すか、運営者に Editor の Test Runner で回してもらう）。テストが 0 件でも成功扱い（終了コード 0）なので、終了コードに加えて結果ファイル（XML）のテストの件数も見る。

## 5. 落とし穴

- **パイプで終了コードを捨てない。** `<コマンド> | tail` は `tail` の終了コードを返すため、失敗が成功に見える。出力はファイルへ落として `echo $?` を別に確認する。
- **画面の文言は E2E でしか守られていない。** 文言だけの変更でも単体テストは緑のまま通る。UI・文言を触ったら push 前に必ず E2E を回す。
- **更新日の古さはコミットの後でしか分からない。** `scripts/check-doc-dates.mjs` は「その文書の内容を最後に変えたコミットの日付」と比べるので、コミット前の実行では古さを見つけられず、CI で初めて赤くなる。docs を編集したら、同じ編集の中で冒頭の「更新日」も直す。コミットが1件も無いリポジトリでは「最初のコミットの後に実行してください」で止まる。
- **`scripts/check-doc-refs.mjs` は `git ls-files` で実在を判定する。** 新しく作ったファイルは stage するまで「実在しない」と報告される。ファイルを追加した変更では先に `git add` する。
- **E2E の1件目の timeout を「flaky（たまに落ちるだけ）」と即断しない。** 編集直後の初回実行は初回コンパイルで時間切れになることがある。編集を挟まず再実行して緑かを見る。逆に、編集していないのに落ちたなら本物の失敗として扱う。
- **落ちた回数ではなく落ちる条件を探す。** 「何回かに1回落ちる」は、溜まったデータ量などで決まる決定的な失敗のことがある。
- **失敗を注入して確かめたら、必ず元へ戻す。** 注入した行・一時ファイルの削除まで含めて1つの作業とする。

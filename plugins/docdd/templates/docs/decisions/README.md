# ADR（Architecture Decision Record）

要件・PRD で表現しきれない**後から変えにくい技術判断**を1判断1ファイルで残す。ファイル名は4桁の連番と短い英語名（例: `0001-use-postgres.md`）。

雛形は `0000-template.md`。「なぜそう決めたか」と「捨てた選択肢」を必ず書く——後で別の人（未来の自分）が同じ検討を繰り返さないため。

## 要決定からの書き戻し

`tasks/BACKLOG.md` の「要決定」で決まったことは、種類で書き戻し先を分ける。要決定に置いたままにしない。

| 決まったこと | 書き戻し先 |
|---|---|
| 事業判断（機能の有無・料金・上限・スコープ） | `docs/PRD.md` の該当節（変更履歴にも1行） |
| 技術判断（フレームワーク・DB・テスト基盤・外部サービスの選定など） | ここに ADR を1本足す |
| 画面・データ・処理の細部 | `docs/requirements/` の担当文書 |

書き戻したら、要決定の「状態」行を書き換える。書き方の例: `決定（2026-10-01, 案A）→ 書き戻し先: ADR-0001`

## ADR 一覧

**手書きの表。ADR を 1 本足したら、同じコミットでこの表にも 1 行足す**（足し忘れは『docs の検査』が落とす）。まだ 1 本も無ければ、見出しと表の頭だけで置いておく。

- 「ADR」の列は本文への相対リンクにする（書き方の例: `[ADR-0001](./0001-use-postgres.md)`）。
- 「状態」は ADR 本文の「状態」行を写す（採用／廃止／置き換え）。
- 「内容」は**何を決めたか**だけを 1 行で書く。件数・金額など正本が別にある数値と、あとからの改訂の経緯は書かない（ADR 本文を読ませる）。

| ADR | 状態 | 内容 |
|---|---|---|

## 決めたことが変わったら

- **一部だけ変わったら本文を書き換えず、冒頭の「改訂」行を書き換える**（書き方の例: `- 改訂: 2026-10-01（T-12）上限を 3 件から 5 件へ`）。2 回目からは下に行を足し、前の行は消さない。
- **判断ごと置き換わるときだけ、新しい ADR を作る。** 古いほうの「状態」を `置き換え（→ ADR-0007）` に書き換え、新しいほうの「背景」で何を引き継ぐかに触れる。**古い ADR は消さない。** 指し先は古いほうの「状態」1 か所だけに置く。
- 補記・追記・`## 改訂` の節のように、形を増やさない。形が 1 つなら、あとから探せる（探し方の例: `grep -n "改訂" docs/decisions/`）。
- PRD・要件詳細は「いまどうなっているか」を書く場所なので、上書きして変更履歴に 1 行。ADR は「そのとき何をなぜ決めたか」の記録なので、上書きしない。

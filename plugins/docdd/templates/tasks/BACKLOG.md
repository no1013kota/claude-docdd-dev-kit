# 開発バックログ

作業キュー。`/docdd:dev-loop` はこのファイルを読んでタスクを選ぶ。

## 運用ルール

- ステータス: `todo` → `doing` → `done`。外部要因で進められないものは `blocked`（理由を必ず書く）、取り下げたものは `dropped`（理由を必ず書く）
- WIP = 1（`doing` は常に1件以下）。1タスク = 1コミット
- 優先順: 上のタスクほど優先。「依存」のタスク・要決定が片付いていないタスクには着手しない（依存先がこのファイルに無ければ、下のアーカイブで `done`・「決定」かを確かめる）
- 並べ替えの基準（どちらを上にするか迷ったとき）: ①**黙って壊れる**（失敗が記録されず、誰も気付けない）→ ②利用者・運営者に実害がある（使えない・お金や情報が失われる）→ ③保守性（同じ直しを何度も繰り返す）→ ④見た目・統一。運営者が「これを先に」と言ったものは、この基準より上に置く
- サイズ: S（半日以内）／M（1日）／L（それ以上。分けて起票する）
- 参照の書き方: `PRD A-1 / requirements/<ファイル名> <見出しID>`。requirements がまだ無ければ `PRD A-1（requirements は本タスクで追記）`。基盤・環境のタスク（テスト基盤・CI など）は `docs/operations/development-and-testing.md §4`
- 振る舞いを変えない改善（リファクタ）も、このキューに起票する。`参照:` は `なし（振る舞いを変えない）` と書き、完了条件に「外部から見た振る舞いが変わらない」を 1 行入れる。候補出しと実行は `/docdd:refactor`
- 終えたタスクは `done` にし、「実装メモ:」（どう作ったか・後続が知るべき判断。1〜2 行）と「検証:」（変更影響表のどの行を回して何を見たか。回さなかった行と理由も同じ 1 行に）の 2 行を足してから、`node scripts/backlog-archive.mjs` で `tasks/archive/BACKLOG-done.md` へ移す。**足すのはこの 2 行だけ**（ラベルを増やすと 1 件が長くなり、アーカイブを検索しても読めなくなる）。このファイルには、まだ動いているもの（`todo`・`doing`・`blocked` と未決の判断）だけを置く（終わったものまで置くと育ち続け、読むだけで作業の場所を使い、末尾の未着手を見落とす）
- ユーザーに判断・準備してほしいことは「要決定・外部準備」に追記する。決まったら「状態」行を書き換え、正本（事業判断は PRD、技術判断は ADR）へ書き戻してから、同じコマンドで移す
- 番号（`T-NN`・`D-N`）は、アーカイブも含めた最大の次にする。二重の起票の確認や過去の経緯は、アーカイブを丸ごと読まず ID や言葉で検索する（例: `grep -n "T-12" tasks/archive/BACKLOG-done.md`）
- 書式の見本（見本なので `/docdd:dev-loop` は拾わない。この形で下の節に書く）:

```markdown
### T-NN: <タスク名> `todo`
- 参照: PRD A-1 / requirements/06_screens.md S-01 / 依存: なし / サイズ: S
- 完了条件:
  - <動作で確認できる形>
  - <異常系・空状態を 1 行>
- メモ: <なぜ必要か・注意点>
（ここから下の 2 行は `done` にするときに足す。アーカイブへ移すと、あとから検索して読む記録になる）
- 実装メモ: <どう作ったか・後続が知るべき判断>
- 検証: <変更影響表のどの行を回して何を見たか／回さなかった行と理由>

### T-NN: <基盤・環境のタスク名> `todo`
- 参照: docs/operations/development-and-testing.md §4 / 依存: <タスクID または なし> / サイズ: S
- 完了条件:
  - <設定と見本 1 件が動く形>
  - <CLAUDE.md「検証コマンド」表のどの行が埋まるか（例: 『単体・DBテスト』『E2E（実際に動かす）』）>

**D-N: <論点>** — <背景 1〜2 文>
- 状態: 未決 ／ 決定（YYYY-MM-DD, 案A）→ 書き戻し先: PRD §4 ／ ADR-0001
- 案A（推奨）: <内容と、選んだときのデメリット>
- 案B: <内容と、選んだときのデメリット>
```
